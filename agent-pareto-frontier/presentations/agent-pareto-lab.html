Agent Pareto Lab

A Cortex Code skill that turns one Cortex Agent config into N committed versions, evaluates each once on the same dataset, attributes billed credits per request, and shows which versions are worth shipping.

N

1

Why "which version do we ship?" stalls

Teams change models and prompts by feel. Without a fixed dataset and real cost per answer, every switch is an argument.

Model choice by anecdote

"The new model felt better on three questions" is not evidence, and nobody re-checks the old version.

Cost is invisible

Agent tokens and the warehouse running Analyst SQL bill separately and lag by hours. Nobody knows credits per answer.

Edits in place

Overwriting the agent or re-running a changed config destroys the comparison you were trying to make.

Broken metrics, found late

A ground-truth key mismatch silently scores every row wrong, and you find out after paying for every run.

Variants are patches on one base spec

Each variant is a short name plus a JSON merge patch. Alias and eval run share one name: <run_prefix>_<name>.

lab.yaml (excerpt, fictional orders agent)

run_prefix: r1
base_spec: specs/base.json
variants:
  - name: baseline              # r1_baseline
    spec: specs/production.json
    warehouse: ORDERS_PARETO_A_WH
  - name: lean                  # r1_lean
    warehouse: ORDERS_PARETO_B_WH
  - name: lean_sonnet55         # r1_lean_sonnet55
    overrides: {models: {orchestration: claude-sonnet-5-5}}
    warehouse: ORDERS_PARETO_C_WH
objectives:
  - {metric: answer_correctness, direction: max}
  - {metric: credits_per_request, direction: min}
constraints:
  answer_correctness: {min: 0.85}

What a variant can change

  • Model: orchestration model (auto vs named)
  • Prompt: orchestration / response instructions
  • Tools: add, remove or re-describe tools and resources
  • Budget: token and time limits
  • Whole spec: e.g. a production replica via spec:
  • Dicts merge, lists replace, null deletes

generate.py --diff shows each variant's diff against the base before anything is created.

Preflight and pilot: break one run, not all of them

The expensive failure is a metric that silently scores every row wrong. The skill catches it before the full launch.

Intake

Ground-truth keys vs metrics

tool_selection_accuracy reads ground_truth_invocations. A dataset with only expected_tools scores every row as "expected 0 tools".

Preflight

Placeholders and "today"

Flags answers like ROAS of X, Y and questions whose truth depends on today, MTD or last week. Checks warehouses exist.

Pilot

Every metric scores

One run on the cheapest variant; per metric, status 200, plausible score, and judge calls showing the expected ground truth.

Partial failures: a run is marked FAILED if any metric fails on any record, even when the agent answered and the other metrics scored. Inspect per-metric data before discarding it.

Cost attribution per request

Each variant gets its own tool warehouse; eval orchestration runs on a separate one. That's what makes credits attributable to a version.

Agent credits

Per request from CORTEX_AGENT_USAGE_HISTORY, joined to the run's requests.

Tool warehouse credits

Analyst SQL runs on the variant's own warehouse, so its metering belongs to that variant only.

Credits per correct answer

Credits per request × questions ÷ answers with correctness ≥ correct_threshold.

Billing lags hours. wait_billing.py exits 0 only when every request is billed. The frontier is not final before that; if you can't wait, label cost as partial. Dollars only with a credit price the customer gives.

Reading the frontier

A variant is dominated when another is at least as good on every objective and better on one. Variants failing a constraint are excluded.

Illustrative chart (not measured data)

How to read it

  • Frontier (blue): no other variant is cheaper and at least as correct. Each is a legitimate choice.
  • Dominated (grey): another variant beats it on every objective. Here the long production prompt costs more for no gain.
  • Excluded (red ring): cheapest, but fails the correctness constraint.
  • State each frontier trade-off plainly: "C costs X more credits per turn for +Y correctness".
  • The first two objectives are the chart axes; more objectives (latency, tokens) still count for dominance.

One run per variant, honest about the gaps

The skill spends budget on more variants, not on repeating the same one. That trade-off has to be stated in the readout.

No repeats

repeats: 1. A repeated run of the same version adds cost but no new option to choose from.

No intervals

With one run there's no confidence interval. A gap of a few points is within run-to-run noise: say so, don't declare a winner.

Read the low scores

Before blaming the agent, check judge explanations in METRIC_CALLS: is it bad ground truth, judge variance, or a real failure?

Ground-truth errors become a new dataset version and a new run_prefix, never an edit to the dataset the runs already used.

Outputs and guardrails

Everything is additive: new versions, new runs, new views. Nothing that a previous round depends on is modified.

Artifacts

  • Agent versions + aliases r1_<name>
  • Eval runs in Snowsight > Evaluations
  • PARETO_R1_* views in the agent's schema
  • frontier.{md,json,svg}, RESULTS.md

Hard rules

  • Never CREATE OR REPLACE the agent
  • Never re-alias or edit a committed version
  • Never reuse a run name or overwrite a config
  • Agent calls via SQL, not the REST API

Teardown

  • Drops the lab warehouses only, after billing
  • Never a shared warehouse (SHOW WAREHOUSES first)
  • Versions on dropped warehouses fail if run again
  • Promote the winner on a permanent warehouse

Next steps

Start with one agent that already has a reviewed dataset and a concrete question: which model, which prompt, what does a correct answer cost.

Pick the comparison

Production vs a lean prompt vs one model swap is a good first round: three variants, one decision.

Get the dataset right first

No dataset, no lab. Run eval-rubric-builder first if ground truth is missing or vague.

Agree the gate

Set the constraints with the customer before running: e.g. correctness ≥ 0.85, no cost increase per request.

Iterate in rounds

Each round is a new run_prefix. Frontier variants seed the next round's patches.
