Dynamic Time-Period Metrics
in Semantic Views

Define once, query at any granularity — monthly, quarterly, yearly — without redefining the view.

Variables Swap time grain at query time
Window Funcs Rolling averages & period-over-period
Combined Multi-grain + comparative metrics

Goal: Calculate metrics dynamically over adjustable time periods (monthly, quarterly, yearly) in a single semantic view, with seamless switching at query time.

The Problem

Business users need to view the same KPIs at different time granularities. Traditional approaches require multiple views or complex SQL.

Without Semantic Views

  • Separate views for monthly, quarterly, yearly
  • Duplicated metric logic across each
  • Manual switching between views
  • Rolling averages require CTEs or subqueries
  • Period-over-period needs self-joins

With Semantic View Features

  • One view with a variable to swap grain
  • Metrics defined once, computed at any grain
  • Query-time grain switching via VARIABLES
  • Window function metrics for rolling calcs
  • LAG/LEAD built into the metric definition

Three Approaches

Depending on your use case, choose one or combine these patterns:

1. Variables

A time_grain variable controls how the time dimension is computed. Change it at query time.

Best for Simple aggregations at swappable grains

2. Window Functions

Metrics that call window functions (AVG OVER, LAG, SUM OVER) on other metrics.

Best for Rolling averages, lag comparisons, running totals

3. Combined

Multiple grain dimensions + window functions per grain. Users pick which to query.

Best for Period-over-period at multiple grains

Pattern 1: Variables for Swappable Time Grain

Define a variable with a default value. Use it in a CASE expression to control the time dimension format.

Docs: Variables Docs: CREATE SEMANTIC VIEW — Variables

CREATE OR REPLACE SEMANTIC VIEW sv_variable_time_grain
  TABLES (
    revenue AS daily_revenue
  )
  VARIABLES (
    time_grain VARCHAR DEFAULT 'month'
  )
  DIMENSIONS (
    revenue.time_period AS
      CASE time_grain
        WHEN 'month'   THEN TO_CHAR(sale_date, 'YYYY-MM')
        WHEN 'quarter' THEN TO_CHAR(sale_date, 'YYYY') || '-Q' || TO_CHAR(QUARTER(sale_date))
        WHEN 'year'    THEN TO_CHAR(sale_date, 'YYYY')
      END,
    revenue.region AS region
  )
  METRICS (
    revenue.total_revenue AS SUM(revenue),
    revenue.avg_daily_revenue AS AVG(revenue)
  )

Key insight: The variable defaults to 'month', so queries work without specifying it. Override with VARIABLES time_grain = 'quarter' to change the grain.

Pattern 2: Window Function Metrics

Define rolling averages, running totals, and lag comparisons directly in the semantic view. Window functions operate on other metrics.

Docs: Window Function Metrics Docs: Querying Window Metrics

METRICS (
  -- Base metric
  revenue.daily_revenue AS SUM(revenue),

  -- Rolling 7-day average
  revenue.rolling_7day_avg AS AVG(daily_revenue)
    OVER (PARTITION BY EXCLUDING revenue.sale_date
          ORDER BY revenue.sale_date
          RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW),

  -- Revenue 7 days ago
  revenue.revenue_7_days_ago AS LAG(daily_revenue, 7)
    OVER (PARTITION BY EXCLUDING revenue.sale_date
          ORDER BY revenue.sale_date)
)

PARTITION BY EXCLUDING — Removes the specified dimension from partitioning. All other dimensions in the query remain. This means the window adapts to whatever grouping the user queries with.

Pattern 2: Rolling Averages in Action

Window function metrics compute automatically when you query them. You must include the ORDER BY dimension in your query.

SELECT * FROM SEMANTIC_VIEW(
  sv_window_metrics
  DIMENSIONS revenue.sale_date
  METRICS revenue.daily_revenue, revenue.rolling_7day_avg, revenue.revenue_7_days_ago
)
WHERE sale_date >= '2024-06-01' AND sale_date <= '2024-06-07'

Pattern 3: Combined — Multiple Grains + Window Functions

Define separate dimensions for each grain and attach window function metrics to each. Users pick which grain to query.

Docs: CREATE SEMANTIC VIEW Docs: SEMANTIC_VIEW Clause

DIMENSIONS (
  revenue.month_period AS TO_CHAR(sale_date, 'YYYY-MM'),
  revenue.quarter_period AS TO_CHAR(sale_date, 'YYYY') || '-Q' || ...,
  revenue.year_period AS TO_CHAR(sale_date, 'YYYY')
)
METRICS (
  revenue.period_revenue AS SUM(revenue),

  -- Month-over-month
  revenue.prior_month_revenue AS LAG(period_revenue, 1)
    OVER (PARTITION BY EXCLUDING revenue.month_period
          ORDER BY revenue.month_period),

  -- Quarter-over-quarter
  revenue.prior_quarter_revenue AS LAG(period_revenue, 1)
    OVER (PARTITION BY EXCLUDING revenue.quarter_period
          ORDER BY revenue.quarter_period),

  -- 3-month moving average
  revenue.moving_avg_3_months AS AVG(period_revenue)
    OVER (PARTITION BY EXCLUDING revenue.month_period
          ORDER BY revenue.month_period
          ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)
)

Limitations & Workarounds

Current constraints to be aware of when combining these features.

Docs: Semantic View Validation Rules Docs: SHOW SEMANTIC DIMENSIONS FOR METRIC

Variables + Window Functions

Variables expand to subqueries internally. These subqueries are not valid GROUP BY expressions when window functions are involved.

Workaround Use Pattern 3 (separate dimensions per grain)

Variable Frame Bounds

You cannot parameterize window frame sizes with variables. INTERVAL my_var PRECEDING is not supported.

Workaround Define separate metrics for each frame (7-day, 30-day, 90-day)

Window Metric Chaining

Window function metrics cannot reference other window function metrics. Each must reference a base metric directly.

Workaround Flatten calculations into a single window expression

Required dimensions: When querying window function metrics, you must include the dimensions referenced in the PARTITION BY EXCLUDING and ORDER BY clauses. Use SHOW SEMANTIC DIMENSIONS ... FOR METRIC to check.

Decision Guide: Which Pattern?

Match the pattern to your use case.

Use CasePatternWhy
Total / average / count at different grains 1: Variables Cleanest syntax; single dimension + variable swap
Rolling averages or lag at a fixed grain 2: Window Functions PARTITION BY EXCLUDING adapts to query dimensions
Period-over-period AND switchable grains 3: Combined Variables can't be used with window funcs; multi-dimension approach works
Simple parameterized thresholds/filters 1: Variables Variables support any scalar expression, not just time
Cumulative YTD totals 2 or 3: Window Functions SUM OVER with ROWS UNBOUNDED PRECEDING

Key Takeaways

Variables are Powerful

A single time_grain variable eliminates the need for multiple views. Default values ensure backward compatibility.

Window Functions Are Native

Rolling averages, LAG/LEAD, and running totals are first-class metric types — no CTEs or self-joins required.

PARTITION BY EXCLUDING Is Key

This clause makes window metrics adaptive — they partition by whatever additional dimensions the user includes in their query.

Know the Boundaries

Variables and window functions can't be combined in the same dimension. Plan your view structure accordingly.
