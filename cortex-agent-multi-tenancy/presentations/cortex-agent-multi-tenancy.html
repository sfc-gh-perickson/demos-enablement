Cortex Agent Multi-Tenancy:
RBAC for 10,000 Users Without Snowflake Accounts

One agent, one service account, per-user data isolation via session attributes and security policies.

10K+ External users — zero Snowflake accounts needed
Row + Column Granular data filtering per user
Immutable Session attributes can't be bypassed
No DDL Add users with INSERT, not role grants

Core pattern: One agent, one service account, per-user data isolation via session attributes + row access policies + masking policies. Your application authenticates users, passes identity as immutable variables, and Snowflake policies enforce boundaries on every query the agent generates.

Docs

The Problem

Why traditional Snowflake RBAC doesn't scale for external-facing AI agents.

External Users

10K users in your IdP with no Snowflake accounts. They access your agent via your app — they don't log in to Snowflake directly.

Per-User Filtering

Each user should only see their own data — rows AND columns. A sales rep sees their deals; a customer sees their invoices.

No Role Explosion

Can't create 10K Snowflake roles. Can't run 10K GRANT statements. Doesn't scale operationally or financially.

Agent-Generated SQL

The agent writes SQL you can't predict. You can't rely on the agent to add WHERE clauses — policies must enforce boundaries regardless of what SQL is generated.

Traditional RBAC requires a Snowflake user per person. Multi-tenancy decouples identity from Snowflake accounts. Your app owns authentication; Snowflake policies enforce data isolation based on session attributes you pass at invocation time.

Session Attributes

Immutable variables passed at invocation time — the foundation of multi-tenant isolation.

-- The agent:run API call with immutable session attributes
POST /api/v2/cortex/agent:run

{
  "agent_name": "my_db.my_schema.support_agent",
  "messages": [{"role": "user", "content": "Show my recent orders"}],
  "variables": {
    "tenant_id": {
      "value": "acme_corp",
      "is_immutable_session_attribute": true
    },
    "user_id": {
      "value": "usr_12345",
      "is_immutable_session_attribute": true
    },
    "access_level": {
      "value": "standard",
      "is_immutable_session_attribute": true
    }
  }
}

Immutable

Cannot be modified by generated SQL, code execution, or tool invocation. A prompt injection attempting ALTER SESSION SET will fail.

Session-Scoped

Persist for the duration of the interaction. Every SQL statement the agent generates within the session sees these attributes.

Multiple Attributes

Pass tenant_id, user_id, access_level, or any custom dimension simultaneously. Policies can reference any combination.

Critical: Always set is_immutable_session_attribute: true. Without this flag, the agent's generated SQL or tool invocations could potentially ALTER SESSION SET a different value, bypassing your security boundaries.

Row Access Policies

Automatically filter rows based on the caller's session attributes — enforced on every query, regardless of SQL shape.

-- Create a row access policy using session attributes
CREATE OR REPLACE ROW ACCESS POLICY tenant_isolation_policy
  AS (tenant_id_col VARCHAR) RETURNS BOOLEAN ->
    tenant_id_col = SYS_CONTEXT('SNOWFLAKE$SESSION_ATTRIBUTES', 'tenant_id')
;
-- Apply the policy to a table
ALTER TABLE orders
  ADD ROW ACCESS POLICY tenant_isolation_policy
  ON (tenant_id);

How It Works

The policy evaluates on every query the agent runs against the table. If the agent generates SELECT * FROM orders, only rows where tenant_id matches the session attribute are returned.

  • No WHERE clause needed in generated SQL
  • Cannot be bypassed by the agent
  • Works with JOINs, CTEs, subqueries
  • Zero performance impact on partition pruning

Compound Policies

Combine multiple attributes for fine-grained control:

CREATE OR REPLACE ROW ACCESS POLICY user_data_policy
  AS (tenant_col VARCHAR, user_col VARCHAR)
  RETURNS BOOLEAN ->
    tenant_col = SYS_CONTEXT(
      'SNOWFLAKE$SESSION_ATTRIBUTES',
      'tenant_id')
    AND user_col = SYS_CONTEXT(
      'SNOWFLAKE$SESSION_ATTRIBUTES',
      'user_id')
;

Column Masking Policies

Hide or mask sensitive columns based on the caller's access level — complementing row-level filtering with column-level protection.

Simple: Direct Attribute Check

Mask based on a single session attribute value:

-- Mask SSN unless access_level = 'admin'
CREATE OR REPLACE MASKING POLICY ssn_mask
  AS (val VARCHAR) RETURNS VARCHAR ->
  CASE
    WHEN SYS_CONTEXT(
      'SNOWFLAKE$SESSION_ATTRIBUTES',
      'access_level') = 'admin'
    THEN val
    ELSE '***-**-****'
  END;

Complex: UDF + Entitlements Lookup

Use a secure UDF to check an entitlements table:

-- Secure UDF checks entitlements
CREATE OR REPLACE SECURE FUNCTION
  has_column_access(col_name VARCHAR)
  RETURNS BOOLEAN
AS
$$
  SELECT COUNT(*) > 0
  FROM entitlements.column_access
  WHERE external_user_id = SYS_CONTEXT(
    'SNOWFLAKE$SESSION_ATTRIBUTES',
    'user_id')
  AND column_name = col_name
$$;

-- Masking policy using the UDF
CREATE OR REPLACE MASKING POLICY
  entitlement_mask
  AS (val VARCHAR) RETURNS VARCHAR ->
  CASE
    WHEN has_column_access('salary')
    THEN val
    ELSE '[REDACTED]'
  END;

When to use each pattern: The direct attribute check is simpler and faster — use it when access rules map cleanly to a small set of levels (admin/standard/restricted). The UDF pattern supports arbitrary per-user, per-column entitlements stored in a table — use it when permissions are dynamic and user-specific.

Entitlements Table Design

Your RBAC control plane — a regular Snowflake table you populate from your IdP, a CSV, or an API sync.

-- The entitlements table: your external RBAC store
CREATE TABLE entitlements.user_entitlements (
  external_user_id  VARCHAR    NOT NULL,
  tenant_id         VARCHAR    NOT NULL,
  access_level      VARCHAR    DEFAULT 'standard',
  allowed_regions   ARRAY,
  allowed_columns   ARRAY,
  created_at        TIMESTAMP  DEFAULT CURRENT_TIMESTAMP(),
  updated_at        TIMESTAMP  DEFAULT CURRENT_TIMESTAMP(),
  PRIMARY KEY (external_user_id, tenant_id)
);
-- Add users via INSERT — no DDL, no role grants
INSERT INTO entitlements.user_entitlements
  (external_user_id, tenant_id, access_level, allowed_regions)
VALUES
  ('usr_12345', 'acme_corp', 'admin', ARRAY_CONSTRUCT('US', 'EU')),
  ('usr_67890', 'acme_corp', 'standard', ARRAY_CONSTRUCT('US')),
  ('usr_11111', 'beta_inc', 'standard', ARRAY_CONSTRUCT('EU'));

-- Bulk load from your IdP sync
COPY INTO entitlements.user_entitlements
  FROM @my_stage/idp_export/users.csv
  FILE_FORMAT = (TYPE = 'CSV' SKIP_HEADER = 1);

This is your RBAC control plane. A regular table you populate from your IdP, a CSV, or an API sync. No Snowflake users, no roles, no grants. When your policies reference this table via a secure UDF, adding or removing access is just an INSERT or DELETE.

Scaling Simply

Compare the multi-tenancy approach against traditional Snowflake RBAC at 10K users.

OperationMulti-Tenancy (This Pattern)Traditional RBAC
Add user INSERT INTO user_entitlements CREATE USER + CREATE ROLE + GRANT ROLE + GRANT PRIVILEGES
Change permissions UPDATE user_entitlements SET access_level = ... REVOKE ROLE + GRANT ROLE (new role)
Remove access DELETE FROM user_entitlements DROP USER + DROP ROLE (cleanup)
New tenant INSERT (rows for new tenant's users) New role hierarchy + grants on all relevant objects
Bulk onboard 1000 users COPY INTO from CSV/stage 1000x CREATE USER + 1000x GRANT statements

Multi-Tenancy Advantages

  • No DDL required for user lifecycle
  • No Snowflake account costs per user
  • Policy changes apply to all users instantly
  • Bulk operations via standard DML
  • Entitlements auditable via standard queries

When Traditional RBAC is Better

  • Internal users who need Snowsight access
  • Users who run their own SQL directly
  • Compliance requiring named Snowflake accounts
  • Fewer than ~50 users with stable roles

The agent:run API Call

Full example: your application layer maps authenticated users to session variables.

-- Full agent:run request with multiple variables
POST /api/v2/cortex/agent:run
Authorization: Bearer <your_service_account_token>

{
  "agent_name": "analytics_db.agents.customer_support",
  "messages": [
    {"role": "user", "content": "What are my open support tickets?"}
  ],
  "variables": {
    "tenant_id": {
      "value": "acme_corp",
      "is_immutable_session_attribute": true
    },
    "user_id": {
      "value": "usr_12345",
      "is_immutable_session_attribute": true
    },
    "access_level": {
      "value": "standard",
      "is_immutable_session_attribute": true
    }
  }
}
-- Your application layer (Python example)
def invoke_agent(authenticated_user, question):
    # Map your app's user to Snowflake session variables
    user_entitlements = get_entitlements(authenticated_user.id)

    response = requests.post(
        f"https://{account}.snowflakecomputing.com/api/v2/cortex/agent:run",
        headers={"Authorization": f"Bearer {service_token}"},
        json={
            "agent_name": "analytics_db.agents.customer_support",
            "messages": [{"role": "user", "content": question}],
            "variables": {
                "tenant_id": {
                    "value": user_entitlements.tenant_id,
                    "is_immutable_session_attribute": True
                },
                "user_id": {
                    "value": authenticated_user.id,
                    "is_immutable_session_attribute": True
                },
                "access_level": {
                    "value": user_entitlements.access_level,
                    "is_immutable_session_attribute": True
                }
            }
        }
    )
    return response.json()

Key point: The service account token authenticates to Snowflake, but the variables block determines what data is visible. A single service account serves all 10K users — the session attributes create per-user isolation within that shared connection.

Best Practices

Patterns that prevent security gaps and operational surprises.

Always Use Immutable Attributes

Without is_immutable_session_attribute: true, a prompt injection could trick the agent into running ALTER SESSION SET to escalate privileges. Immutable = non-negotiable.

Scope Narrowly

Only pass variables needed per request. Don't pass a "superuser" attribute that grants broad access — pass the minimum context needed for the specific interaction.

Test Policies Independently

Before deploying to an agent, verify policies manually with ALTER SESSION SET and run queries directly. Confirm filtering before adding the agent abstraction layer.

Entitlements Caching

Use secure UDFs for complex lookups — Snowflake caches UDF results within a session, reducing repeated entitlements table scans.

Cortex Search Filtering

RAPs do NOT apply to Cortex Search results. For search-based agents, create separate search services per tenant, or pre-filter source tables before indexing.

Policy on Every Table

Apply row access policies to all tables the agent can access. A single unprotected table is a data leak. Audit with POLICY_REFERENCES function.

Cortex Search limitation: Row access policies are enforced by the SQL execution engine. Cortex Search uses a vector index — it bypasses RAPs. If your agent uses Cortex Search, you must pre-filter data at indexing time or create per-tenant search services. This is a common gap in multi-tenant agent deployments.

Audit & Observability

Correlate agent usage with your application's auth logs for complete audit trails.

-- Query agent usage and correlate with your app's user context
SELECT
  request_id,
  START_TIME,
  AGENT_NAME,
  TOKENS_USED,
  CREDITS_USED,
  METADATA
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_AGENT_USAGE_HISTORY
WHERE AGENT_NAME = 'ANALYTICS_DB.AGENTS.CUSTOMER_SUPPORT'
  AND START_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
ORDER BY START_TIME DESC;
-- Join with your application logs for full traceability
-- Your app logs: (request_id, external_user_id, tenant_id, timestamp)
-- Pattern: log the request_id from agent:run response in your app

SELECT
  app.external_user_id,
  app.tenant_id,
  sf.TOKENS_USED,
  sf.CREDITS_USED,
  sf.START_TIME
FROM app_logs.agent_requests app
JOIN SNOWFLAKE.ACCOUNT_USAGE.CORTEX_AGENT_USAGE_HISTORY sf
  ON app.request_id = sf.request_id
WHERE sf.START_TIME >= DATEADD('day', -30, CURRENT_TIMESTAMP())
ORDER BY sf.START_TIME DESC;

What to Log in Your App

  • request_id from agent:run response
  • Authenticated user identity
  • Variables passed (tenant_id, user_id)
  • Timestamp and user question

This creates the bridge between Snowflake's usage views and your user identity — essential for per-user cost attribution and security audits.

Observability Stack

  • CORTEX_AGENT_USAGE_HISTORY — token/credit costs per request
  • QUERY_ATTRIBUTION_HISTORY — warehouse compute from generated SQL
  • Your app logs — user identity, tenant context
  • Combined: full cost-per-user-per-tenant attribution

Summary

  • Session attributes decouple user identity from Snowflake accounts — scale to 10K+ users with zero DDL
  • is_immutable_session_attribute prevents prompt injection from escalating privileges
  • Row access policies filter rows on every query — regardless of agent-generated SQL
  • Masking policies hide columns based on access level or entitlements lookups
  • RAPs do NOT apply to Cortex Search — pre-filter or use per-tenant search services

Getting Started

  • Step 1: Create entitlements table with external_user_id + tenant_id
  • Step 2: Create row access policy using SYS_CONTEXT
  • Step 3: Apply policy to all agent-accessible tables
  • Step 4: Create masking policies for sensitive columns
  • Step 5: Test with ALTER SESSION SET before agent deployment
  • Step 6: Update app layer to pass immutable variables on agent:run

Multi-tenancy is not optional for production external-facing agents. Without it, every user sees every row. Session attributes + policies give you per-user isolation with zero per-user infrastructure.
