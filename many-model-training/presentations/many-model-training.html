The Problem

Global Models Miss Local Patterns

One model for all stores averages away store-specific behavior. A downtown express store and a rural highway store have fundamentally different demand curves.

Multi-Tool Pipeline Sprawl

Data moves through 5+ systems: warehouse → scheduler → storage → compute → event bus. Each hop adds latency, failure points, and security surface.

Manual Retraining

Retrain everything weekly on a schedule, not when models actually degrade. You waste compute on healthy models and miss drift in degraded ones.

No Explainability

Predictions are opaque — can't explain why 10 items were predicted for this hour. Store managers can't trust or override what they don't understand.

Snowflake ML solves these with native, unified infrastructure — features, training, inference, and monitoring all in one platform with zero data movement.

Feature Store: Versioned, Reproducible Features

Concepts

Entity defines the grain — the unit you're modeling (store-item combination, device, customer segment).

FeatureViews group related features and manage refresh schedules via Dynamic Tables.

Versioning enables safe experimentation — roll back features without breaking production models.

Registration

from snowflake.ml.feature_store import (
    FeatureStore, Entity, FeatureView
)

# Define the entity grain
store_item = Entity(
    name="STORE_ITEM",
    join_keys=["STORE_ID", "ITEM_ID"]
)
fs.register_entity(store_item)

# Register a FeatureView from a DT
fv = FeatureView(
    name="DEMAND_FEATURES",
    entities=[store_item],
    feature_df=feature_df,
    refresh_freq="60 minutes"
)
fs.register_feature_view(fv, version="v1")
Point-in-time correct joins — the Feature Store automatically handles temporal alignment so training data never leaks future information into historical features.

Distributed Partition Training

from snowflake.ml.modeling.distributedpartitionfunction import ManyModelTraining

trainer = ManyModelTraining(
    session=session,
    input_table="MMT_DEMO.FORECASTING.TRAINING_DATA",
    partition_column="STORE_ITEM_KEY",
    target_column="UNITS_SOLD",
    feature_columns=["HOUR_OF_DAY", "DAY_OF_WEEK", "IS_HOLIDAY",
                     "ROLLING_7D_AVG", "PROMO_ACTIVE", "WEATHER_TEMP"],
    model_type="xgboost",
    compute_pool="ML_TRAINING_POOL",
    experiment_name="demand_forecast_champion"
)

# Train all partitions in parallel
results = trainer.fit()

DPF Distribution

Distributed Partition Function automatically shards data by partition key and trains models across compute pool nodes in parallel.

XGBoost + SHAP

Each partition gets its own XGBoost model with SHAP feature importances — store managers can see why predictions are what they are.

Train/Val Split

80/20 temporal split per partition. Validation metrics (MAE, RMSE, MAPE) are computed honestly — no leakage across time boundaries.

Per-Partition Metrics

MAE, RMSE, MAPE, and feature importances saved per partition. Identify which store-items train well and which need attention.

Model Registry: Partitioned Inference

from snowflake.ml.registry import Registry
from snowflake.ml.model import CustomModel
from snowflake.ml.model.custom_model import partitioned_api

class DemandForecastModel(CustomModel):
    @partitioned_api(partition_column="STORE_ITEM_KEY")
    def predict(self, input_df):
        # Each partition routes to its trained sub-model
        model = self.context.artifacts["models"][partition_key]
        predictions = model.predict(input_df[self.feature_columns])
        return predictions

# Register in Model Registry
reg = Registry(session)
mv = reg.log_model(
    model=demand_model,
    model_name="DEMAND_FORECAST",
    version_name="champion_v1",
    target_platforms=["warehouse", "spcs"]
)

Register Once

A single model registration encapsulates all 1,000+ partition sub-models. The @partitioned_api decorator handles routing automatically during inference.

Target Platforms

Deploy to warehouse (SQL-callable) or SPCS (container-based) with the same registered model. Switch platforms without retraining.

Batch Inference at Scale

predictions = mv.run(

Distributed Scoring

The Model Registry routes each partition's input to its specific trained model. 1,000 partitions score in parallel — no manual fan-out logic needed.

SHAP Explanations

Each prediction includes feature importance scores. Store managers see that temperature and day-of-week drove the forecast, not a black-box number.

Telemetry Integration

Predictions automatically feed the monitoring pipeline. Actuals arrive later and are joined to compute error metrics per partition.

Scheduling

Wrap mv.run() in a Snowflake Task for hourly/daily batch scoring. Dynamic Tables refresh features upstream automatically.

Automated Drift Detection

-- Rolling MAPE per partition over the last 7 days
SELECT
    STORE_ITEM_KEY,
    AVG(ABS(ACTUAL - PREDICTED) / NULLIF(ACTUAL, 0)) AS ROLLING_MAPE,
    CASE WHEN ROLLING_MAPE > 0.25 THEN 'DRIFTED' ELSE 'HEALTHY' END AS STATUS
FROM MMT_DEMO.FORECASTING.TELEMETRY
WHERE PREDICTION_TS > DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY STORE_ITEM_KEY;

Drift Pipeline

1. Predictions land in telemetry table with timestamps

2. Actuals join when available (hourly for demand)

3. Rolling error metrics computed per partition

4. Partitions exceeding threshold flagged for retraining

5. Only flagged partitions retrain — not the entire fleet

Telemetry Table Schema

CREATE TABLE TELEMETRY (
  STORE_ITEM_KEY VARCHAR,
  PREDICTION_TS  TIMESTAMP,
  PREDICTED      FLOAT,
  ACTUAL         FLOAT,
  MAPE           FLOAT,
  MODEL_VERSION  VARCHAR,
  FEATURE_HASH   VARCHAR
);
Retrain only the 5% of models that degrade — not the entire fleet. Selective retraining saves 95% of compute while keeping every partition accurate.

Champion vs Challenger

experiment = ExperimentTracking(
    session=session,
    name="demand_forecast_experiment",
    champion_model="DEMAND_FORECAST/champion_v1",
    challenger_model="DEMAND_FORECAST/challenger_v1",
    partition_column="STORE_ITEM_KEY",
    metric="MAPE",
    objective="minimize"

results = experiment.evaluate()

AI-Powered Model Monitoring

A Cortex Agent with Analyst + Search tools provides interactive, data-grounded monitoring of the entire model fleet.

-- Create a monitoring agent with tools for telemetry and insights
CREATE AGENT MMT_MONITORING_AGENT FROM SPECIFICATION $$
tools:
  - tool_spec:
      type: "cortex_analyst_text_to_sql"
      name: "telemetry_analyst"
      description: "Queries model telemetry, drift flags, and experiment results"
  - tool_spec:
      type: "cortex_search"
      name: "insights_search"
      description: "Retrieves past monitoring insights and recommendations"
tool_resources:
  telemetry_analyst:
    semantic_view: "MMT_DEMO.FORECASTING.MMT_TELEMETRY_VIEW"
  insights_search:
    name: "MMT_DEMO.FORECASTING.INSIGHTS_SEARCH_SVC"
$$;

-- Query the agent naturally
SELECT SNOWFLAKE.CORTEX.AGENT(
    'MMT_MONITORING_AGENT',
    'Which models are drifting and what should we retrain?'
):content::VARCHAR;

Cortex Analyst Tool

Queries telemetry data via a semantic view — the agent writes SQL to answer questions about MAPE, drift flags, experiments, and model catalog metadata.

Cortex Search Tool

Retrieves past insights and recommendations. Enables the agent to say "this partition drifted last month too — the fix was adding weather features."

Statistical Pre-Analysis

SQL-based drift detection and feature distribution analysis runs first (no LLM needed). The agent synthesizes structured findings into actionable reports.

From alert to action — instead of just flagging "MAPE > 25%", the monitoring agent explains why the model drifted and recommends whether to retrain, add features, or investigate upstream data quality.

Scaling to Production

Compute Pool Sizing

Add nodes to the compute pool for more partitions. DPF automatically distributes work across available nodes — linear scaling with no code changes.

Partition Counts

The same code works for 100 or 100,000 partitions. DPF handles the fan-out. Start small, grow to full catalog without refactoring.

Dynamic Table Refresh

Features refresh on a schedule via Dynamic Tables. As source data updates, features recompute incrementally — no manual orchestration.

Snowflake Tasks

Schedule training, inference, and drift detection with native Tasks. CRON expressions, DAG dependencies, and automatic retries built in.

-- Schedule daily inference via Snowflake Task
CREATE TASK MMT_DEMO.FORECASTING.DAILY_INFERENCE
  WAREHOUSE = ML_WH
  SCHEDULE = 'USING CRON 0 6 * * * America/Chicago'
AS
  CALL MMT_DEMO.FORECASTING.RUN_INFERENCE();

-- Schedule drift check after inference completes
CREATE TASK MMT_DEMO.FORECASTING.DRIFT_CHECK
  AFTER MMT_DEMO.FORECASTING.DAILY_INFERENCE
AS
  CALL MMT_DEMO.FORECASTING.CHECK_DRIFT();
