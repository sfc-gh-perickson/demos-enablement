The Problem: Fraud Rings in Tax Filing

Multiple fraudulent applicants operating from the same apartment, sharing IPs, devices, and bank accounts — filing bogus claims for payouts.

Shared Addresses

Dozens of returns filed from a single apartment unit. Traditional rules catch obvious cases but miss sophisticated rings.

Shared Infrastructure

Same IP addresses, device fingerprints, and bank accounts used across seemingly unrelated applicants.

Evolving Patterns

Rings adapt — rotating addresses, using VPNs, splitting across submission dates. Point-in-time rules can't keep up.

Why graph analytics? Fraud rings are fundamentally a network problem. Community detection algorithms like Leiden find clusters of connected applicants that rules-based systems miss — even when individual transactions look normal.

GPU-Accelerated Leiden Community Detection

NVIDIA cuGraph on Snowpark Container Services

Why Leiden?

Leiden improves on Louvain with guaranteed connected communities and better resolution control. Ideal for detecting tightly-knit fraud rings of varying sizes.

Why GPU?

3M nodes and 9M edges is too large for pure-SQL or CPU graph algorithms at interactive speeds. cuGraph on a single GPU completes in seconds.

SPCS Job Service

Container starts, reads edges via Snowpark, runs Leiden + centrality, writes results back, exits. GPU released on completion — no idle cost.

Benchmark: 3M Nodes / 9M Edges on GPU_NV_S

Key insight: Leiden itself runs in single-digit seconds on GPU. The bottleneck is I/O — reading edges from Snowflake and writing results back. Actual benchmark timings are captured in the SPCS job logs and demonstrated live in the notebook.

Three-Entity Coverage: No Applicant Left Behind

ADDRESS and IP entities provide inherited community context for new applicants

ADDRESS Entity

Aggregates community members per application address. A brand-new applicant at a known fraud-ring address immediately inherits that community's features — dominant community, number of applicants, average claim.

IP_NETWORK Entity

Same approach for IP addresses. An applicant sharing an IP with known ring members gets inherited community context, even with no direct Leiden assignment yet.

Model Training via ML Jobs + Tuner HPO

XGBoost fraud classifier with 15 graph-community features

1. Generate Training Set

Feature Store generate_training_set() creates point-in-time correct data by joining APPLICATIONS spine (with IS_FRAUD labels) against the 3 batch FVs.

2. ML Job V1 (Baseline)

Training script submitted via submit_directory() to ML_TRAINING_POOL. ExperimentTracking logs metrics. Registered as V1 with SPCS target.

3. Tuner HPO V2

BayesOpt hyperparameter optimization — 10 trials across 5 params (n_estimators, max_depth, learning_rate, scale_pos_weight, min_child_weight). Best trial registered as V2.

15 features, three signal families: Graph-structural (community size, degree, shared counts), address/IP-inherited (applicant count, avg claim at shared locations), and velocity (submission hour, claim amount, high-claim flag). The model learns that HAS_DIRECT_GRAPH=0 + ADDR_N_APPLICANTS > 10 = "new applicant at suspicious address" — no hand-crafted risk score needed.

Model Monitoring: Drift Detection

Automated observability for production fraud scoring

Inference Autocapture

A Dynamic Table reads INFERENCE_TABLE() every 10 minutes, extracting all 15 features + predictions from the SPCS service logs. Zero instrumentation code needed.

Monitoring Baseline

5,000-row snapshot from the training distribution, cast to FLOAT. This is the reference for PSI drift detection — how does production data compare to what the model was trained on?

Model Monitor

Tracks PSI (Population Stability Index) drift on CLAIM_AMOUNT with daily refresh and aggregation. Alerts when the production distribution shifts from the training baseline.

Why monitor? Fraud rings adapt. If ring members shift to lower claim amounts or different submission patterns, PSI drift on CLAIM_AMOUNT catches the distribution change before accuracy degrades — triggering retraining with fresh labels.

Case A: Suspicious Applicant

Shares address with known fraud ring members. ADDRESS entity provides inherited community features (large community, high applicant count). Model receives 15 features via Gateway and scores HIGH RISK — even before Leiden processes the filer directly.

Case B: Clean Applicant

Unique address, unique IP — no inherited community context. Real-time FV falls through to zero for entity-inherited features. Model scores on velocity and claim features only. Scores LOW RISK.

The link between graph analytics and real-time ML: Leiden community features flow through three entities — APPLICANT (direct), ADDRESS (inherited), IP_NETWORK (inherited). The real-time FV assembles 15 raw features; the model learns which combinations indicate fraud. Full Leiden corrects every 15 minutes. The Gateway routes to the best model version automatically.
