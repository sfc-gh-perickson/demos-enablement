The problem

A great demo is not a production system

LLM outputs look right in a handful of examples and fail quietly at scale. Teams need the same discipline they apply to code: tests, versioning, and monitoring.

Plausible but wrong

Looks right, breaks downstream

"Setup / Feature Configuration" reads well but isn't a valid category, so routing rules and dashboards miss it.

Unmeasured

"It seemed fine" isn't a metric

Without a labeled set and a score, you can't compare prompts or models, or tell whether a change helped.

Cost blind

The premium model by default

Smaller models are often far cheaper, but only a measured cost-vs-quality comparison tells you if they're good enough.

Drift

Inputs change after launch

New products, seasons, and policies shift the input mix. Quality can degrade with no error ever raised.

Demo use case

Support-ticket triage with structured output

One AI_COMPLETE call extracts five fields and an escalation decision. response_format guarantees valid JSON with the right keys.

-- Ticket (input)
"I've contacted support twice about my
AeroBlend Pro Blender (order ORD-90837) and
was charged twice. I'm fed up. Please refund
the duplicate charge."

-- Structured output
{
  "product":          "AeroBlend Pro Blender",
  "issue_type":       "billing",
  "sentiment":        "negative",
  "requested_action": "refund",
  "order_id":         "ORD-90837",
  "escalation_flag":  true
}

Taxonomy fields

issue_type: billing, shipping, defect, safety, account, how_to
sentiment: negative, neutral, positive
requested_action: refund, replacement, repair, information, cancel_order

Extraction fields

product, order_id (or null if absent)

Business-rule flag

escalation_flag = safety issue or legal threat or (negative tone and repeat contact)

Evaluate before production · Step 1

Build a golden dataset, then freeze it

The golden set is your test suite. Make it representative, keep part of it hidden, and version it so every score is reproducible.

Representative

  • Cover every category and edge case
  • Include the hard ones: ambiguous tone, missing IDs, policy edge cases
  • 20–50 rows is enough to iterate; experiments accept up to 1,000

Split

  • Train (50): what the optimizer learns from
  • Holdout (50): never seen during tuning, used for the final score
  • Production stream (200): unlabeled

Versioned

  • CREATE DATASET + ADD VERSION 'v1'
  • Versions are immutable snapshots
  • Label fixes become v2, so old scores stay comparable
CREATE DATASET EVAL.TICKETS_HOLDOUT;
ALTER DATASET EVAL.TICKETS_HOLDOUT ADD VERSION 'v1' FROM (SELECT ticket_text, expected FROM EVAL.HOLDOUT);
Evaluate before production · Step 2

Pick metrics that match the task

Use an LLM judge for an overall verdict, plus deterministic per-field checks to see exactly what's failing.

$$;

Optimize

Let the optimizer search prompts and models

One experiment tunes the whole function body for several models at once, from budget to premium, and scores finalists on the hidden holdout set.

1

Seed

Starts from your current function body and score.

2

Reflect

A reflection model reads the judge's per-row feedback and proposes edits to the prompt, schema, and SQL.

3

Select

Keeps Pareto-best candidates per model on quality vs cost (GEPA).

4

Verify

Scores frontier candidates on the holdout set and records cost relative to the seed.

CREATE EXPERIMENT TRIAGE_TICKET_OPT_EXP TYPE = 'AI_FUNCTION_OPTIMIZATION' FROM SPECIFICATION $$
  function: { function_name: AI_FUNCTIONS_EVAL_DEMO.EVAL.TRIAGE_TICKET }
  metrics:  [{ name: llm_judge, judge_model: claude-sonnet-4-6 }]
  dataset:  { name: ...TICKETS_TRAIN, version: v1, holdout_data: ...TICKETS_HOLDOUT, holdout_version: v1,
              column_mapping: { argument_mapping: { TICKET_TEXT: TICKET_TEXT }, ground_truth: EXPECTED } }
  optimization: { models: [openai-gpt-5-nano, ministral-3-8b, claude-sonnet-4-6], budget: light }
$$;
Optimize

What the optimizer changed

It rewrote the whole function body, not just a sentence of the prompt.

Schema

Added enum constraints

The output schema now lists allowed values, so free-text categories can't be produced at all.

Decision rules

Tie-breakers for hard cases

Explicit guidance for defect vs how_to and for judging the writer's tone, not the problem's severity.

Inferred policy

Guessed the escalation rule

It inferred "2+ prior contacts" from examples. The real rule is "negative tone and any repeat contact." Close, but not right.

"issue_type": {"type": "string", "enum": ["billing","shipping","defect","account","how_to","safety","other"]},
  "sentiment: Judge OVERALL TONE and WARMTH of the writer, NOT the severity of the problem..."
  "Decision aid for defect vs how_to: Ticket asks how to reset/configure, references unclear manual => how_to"

Note the "other" value: the optimizer added a category the business doesn't use. Production monitoring catches this later.

Optimize · Lesson 3

Some "model errors" are label errors

Escalation accuracy stalled at 76%, even after we wrote the business rule into the prompt. When a field won't move, review the disagreements, not just the prompt.

In production

Deploy patterns that keep you in control

Ship what you measured

Promote a run directly from the experiment, with no copy-pasting prompts.

CREATE AI FUNCTION PROD.TRIAGE_TICKET(TICKET_TEXT VARCHAR)
  RETURNS VARIANT
  FROM EXPERIMENT EVAL.TRIAGE_TICKET_OPT_EXP RUN ITER_21;

Incremental & versioned

A stream + task processes only new tickets, and every row records which function version produced it.

INSERT INTO TRIAGE_RESULTS
SELECT ticket_id, ..., 'opt_v2', TRIAGE_TICKET(ticket_text)
FROM INCOMING_TICKETS_STREAM;

Attributable cost

Tag the workload so usage history can split its cost from everything else on the account.

CREATE TASK TRIAGE_TICKETS_TASK ...
  QUERY_TAG = '{"app":"ticket_triage","env":"prod"}'

Gate every change

Treat a prompt or model change like a code change. It ships only if the evaluation experiment on the current golden-set version passes your bar.

In production

Four signals, no ground truth required

Production has no labels, so combine cheap deterministic checks with a small, sampled LLM review.

Cost

Credits & tokens

CORTEX_AI_FUNCTIONS_USAGE_HISTORY filtered by QUERY_TAG: credits per day, per model, per 1K tickets.

Health

Output conformance

SQL checks: values in taxonomy, null results, ID formats. Free, real-time, and catches schema regressions.

Drift

Distribution shift

Escalation and negative-sentiment rates in production vs the golden set. Large shifts mean the inputs or the model changed.

Quality

Sampled LLM review

A daily task asks a judge model to audit ~20 random production rows against the business rules.

Alerting: a Snowflake ALERT checks all four signals hourly and notifies the owning team (email, Slack, or webhook) when a threshold is crossed.

Continuous improvement

Close the loop

Production findings become test cases. The golden set grows with your business, and every change is measured against it.

Monitor flags rows→ Review & label→ DATASET vn+1→ Re-evaluate→ Re-optimize→ Deploy vn+1↻

Weekly

Review alert log and judge-flagged rows, then label and add them to the golden set.

On every change

New prompt, model, or policy: run the evaluation experiment; ship only if it beats the current version.

Quarterly

Re-run optimization across current models; newer, cheaper models may now clear the bar.

Takeaways

Production-readiness checklist

  • Wrap the prompt as a governed AI FUNCTION with structured output
  • Build a representative golden set and freeze it as a versioned DATASET
  • Keep a holdout set; never ship on the validation score
  • Score with an LLM judge and per-field checks
  • Optimize across several models; choose on measured cost vs quality
  • Write known business rules down explicitly; don't rely on the optimizer to infer policy
  • Review model–label disagreements; fix labels in a new version
  • Deploy from the experiment; log the function version on every row
  • Tag workloads and monitor cost, health, drift, and sampled quality
  • Alert on thresholds and feed findings back into the golden set
