Part 1

Theory: Why and What to Evaluate

The Trust Problem

An agent's answer may appear successful, but the path it took to get there may not be.

Hidden Failures

Agents can produce correct-looking answers through incorrect reasoning, wrong tool usage, or hallucinated intermediate steps that happen to reach the right conclusion.

Wasted Compute

Inefficient tool calling, redundant steps, and poor planning inflate latency and cost without any visible signal to end users or operators.

Wrong Decisions

Enterprise agents power business workflows serving thousands of users. Inaccurate outputs lead to incorrect business decisions at scale.

Eroded Trust

Without visibility into agent behavior, teams lose confidence in deployments. One undetected regression can undermine months of adoption progress.

The core challenge: Outcome-focused evaluation confirms whether an agent succeeded, but provides little insight into why it failed or how to fix it. We need evaluation that covers the full reasoning pipeline.

The Agent GPA Framework

Snowflake AI Research's Goal-Plan-Action framework evaluates agents across three critical phases of reasoning and execution.

Goal

Was the response relevant, grounded, and accurate from the user's perspective?

Answer Correctness Answer Relevance Groundedness

Plan

Did the agent design a sound roadmap, selecting appropriate tools for each step?

Plan Quality Tool Selection

Action

Were tools executed effectively with correct parameters and appropriate use of outputs?

Plan Adherence Tool Calling

Cross-Cutting Metrics

These span the full Goal-Plan-Action chain:

Logical Consistency Execution Efficiency

Checks for contradictions, ignored instructions, redundant steps, and wasted resources across the entire trace.

Benchmark Results (TRAIL/GAIA)

Tested against 570 human-annotated agent errors:

  • 95% error detection (vs. 55% baseline)
  • 86% error localization (vs. 49% baseline)
  • Coverage across low, medium, and high-impact failures

Key insight: Agent GPA makes agent behavior observable and debuggable. Instead of treating agents as black boxes, you can pinpoint exactly where in the reasoning chain quality degrades.

Evaluating Agent Tools & Skills

Cortex Agents compose multiple tool types to answer queries. Each tool introduces distinct failure modes that require targeted evaluation strategies.

Cortex Search

RAG-based retrieval over unstructured data (documents, knowledge bases, support articles).

Evaluate:

  • Was the right context retrieved? (retrieval relevance)
  • Did the agent ground its answer in retrieved content? (groundedness)
  • Were irrelevant passages filtered out? (precision)

Cortex Analyst (Semantic Views)

Structured data access via natural language to SQL generation over semantic models.

Evaluate:

  • Was the correct semantic view selected?
  • Did the generated SQL produce accurate results? (answer correctness)
  • Were verified queries leveraged when available?

Agent Skills

Custom tools defined via markdown or code that extend the agent with domain-specific capabilities.

Evaluate:

  • Was the correct skill invoked for the task?
  • Were parameters passed correctly?
  • Did the skill output get interpreted and communicated accurately?

Tool Orchestration

The agent's planning layer decides which tools to invoke, in what order, and how to combine their outputs.

Evaluate:

  • Did the agent choose the right tool for the query intent?
  • Were multi-tool queries decomposed correctly?
  • Was the orchestration efficient (no redundant calls)?

Implication for evaluation datasets: Your eval set should include queries that exercise each tool type individually AND queries that require multi-tool coordination. A dataset focused only on search queries won't catch failures in SQL generation or skill invocation.

Semantic View quality matters: If your semantic view has poor descriptions, ambiguous metrics, or missing verified queries, the agent will generate incorrect SQL regardless of how good the orchestration LLM is. Evaluate your semantic view quality independently using description audits and verified query coverage.

Designing Evaluation Datasets

Your evaluation is only as good as the data it tests against. Build datasets that reflect real-world usage distribution.

Represent All Intent Types

  • Happy paths (common, expected usage)
  • Edge cases and bad paths
  • High-risk queries (financial, compliance)
  • Out-of-scope / refusal scenarios

Prioritize High-Stakes Areas

Measure not only macro correctness but also intent-level performance. You need confidence that the agent behaves correctly in high-value, high-stakes scenarios — not just on average.

Source Questions Strategically

Curate questions from SMEs who know the business domain, use synthetic generation to cover edge cases, or mine production logs if available. All three approaches are valid — the key is covering the full intent distribution, not where the questions originated.

Ground Truth Best Practices

  • Specific enough to validate, not so specific that non-determinism causes false negatives
  • Anchor to fixed time periods to avoid staleness
  • Describe what correct looks like, not just a single "right answer"
  • Include what the response should NOT contain

Evaluation Rubrics & Metrics

A rubric is a collection of metrics that score the agent's performance. Choose metrics aligned with your specific business requirements.

Built-in System Metrics

MetricTypeRequires
Answer Correctness Ground truth Expected output
Logical Consistency Reference-free Nothing extra

Logical consistency evaluates the full execution trace: instructions, planning, and tool calls for internal coherence — no ground truth needed.

Custom Metric Examples

  • Brand compliance — speaking in voice, no competitor mentions
  • Context relevance — did RAG retrieve correct documents
  • Groundedness — claims supported by retrieved context
  • Tool selection accuracy — chose the right tool for the task
  • Response completeness — addressed all parts of the query
  • Citation quality — references point to real sources
# Custom metric YAML configuration
metrics:
  - name: "groundedness"
    score_ranges:
      min_score: [0, 0.33]
      median_score: [0.34, 0.66]
      max_score: [0.67, 1]
    prompt: |
      You are evaluating the groundedness of an AI agent's response.
      User Query: {{input}}
      Agent Response: {{output}}
      Expected Answer: {{ground_truth}}

      Rate whether each statement in the response is supported
      by the tool outputs and retrieved data in the execution trace...

Template variables available: {{input}}, {{output}}, {{ground_truth}}, {{tool_info}}, {{duration}}, {{span_type}}, {{llm_model}}, {{error}}, {{status}} — the full agent execution trace is always provided to the LLM judge as context.

LLM-as-a-Judge Methodology

Evaluation at scale requires automated scoring. LLM judges grade agent responses against your rubric — but they must be calibrated to match human judgment.

Trace-Level vs. Step-Level

Trace-Level Evaluation

Did the agent produce the correct final output? Evaluates the end-to-end result against ground truth.

Step-Level Evaluation

Did the agent use the correct tools with the correct parameters at each step? Evaluates intermediate reasoning and execution decisions.

Both are necessary: An agent can reach the right answer through wrong steps, or take all the right steps but produce a poor final answer.

Judge Calibration Process

The LLMAJ Tuning Loop

  1. Collect agent traces (question + trace + response triples)
  2. Have human SMEs grade them across your rubric
  3. Run LLM judges with initial prompts on the same data
  4. Measure correlation using Cohen's Kappa
  5. Iterate judge prompts until 80%+ correlation on dev/test splits

Why calibration matters: An uncalibrated LLM judge introduces uncertainty into your metrics. By achieving 80%+ Cohen's Kappa correlation with human annotators, you reduce the error bars on scores and can trust automated evaluations to approximate expert judgment.

Part 2

Practice: How to Evaluate and Iterate

Monitoring is Not Evaluation

Teams often delay or skip evaluation for reasons that don't hold up under scrutiny. If your agent is critical enough to deploy, it's critical enough to evaluate.

"It costs too much"

"We paused evals because of the cost of LLM judge calls."

Reality: A 50-question eval with 3 metrics = ~150 judge calls. That's a fraction of a cent per question. Compare this to the cost of a wrong business decision delivered confidently to thousands of users. If the agent is business-critical, the cost of NOT evaluating is orders of magnitude higher.

"VQRs make evals redundant"

"Once we add verified queries, the eval dataset is just testing cached answers."

Reality: VQRs are a production guardrail that ensures determinism on known high-value queries. Evaluations measure reasoning quality on novel queries, tool selection across the long tail, multi-step coordination, and behavior on inputs your VQRs don't cover. They serve fundamentally different purposes.

"Our monitoring dashboard is enough"

"We track latency, SQL failure rates, and tool distribution."

Reality: Monitoring measures operational health — did the SQL execute? How long did it take? Evaluation measures correctness — did the SQL return the right answer? A query that executes successfully but returns wrong results is invisible to monitoring. Only evaluation catches it.

What monitoring tells you

  • SQL execution success/failure rates
  • Latency and token consumption
  • Tool call distribution and frequency
  • Error rates and availability

What only evaluation tells you

  • Was the answer actually correct?
  • Did the agent select the right tool for this query?
  • Was the reasoning path sound or did it get lucky?
  • How does behavior change on novel inputs outside VQR coverage?

The real question isn't "can we afford to evaluate?" — it's "can we afford to serve business users with an agent whose correctness we haven't measured?" Every agent that's worth deploying is worth evaluating.

Agent Versioning for Safe Iteration

Evaluation without version control is like testing without source control. Versioning gives you immutable checkpoints to compare, promote, and rollback.

-- Make changes on the live version
ALTER AGENT my_agent SET
  INSTRUCTIONS = 'Updated system prompt...';

-- Commit to create an immutable snapshot for evaluation
ALTER AGENT my_agent COMMIT
  COMMENT = 'Improved tool selection logic';

-- Promote after evaluation passes
ALTER AGENT my_agent
  MODIFY VERSION VERSION$4 SET ALIAS = production;

Important: Always use ALTER AGENT to iterate. CREATE OR REPLACE AGENT is destructive — it deletes all past evaluation runs, monitoring traces, and version history.

Running Evaluations in Snowflake

Three paths to run evaluations: Snowsight UI, SQL, or Cortex Code. All produce the same results.

Snowsight UI

AI & ML → Agents → Select agent → Evaluations tab → New evaluation run. Visual interface for selecting datasets, metrics, and viewing results.

SQL

Programmatic via EXECUTE_AI_EVALUATION. Best for CI/CD pipelines and scheduled evaluation tasks. Uses a YAML config file on a stage.

Iterating on Your Agent

Once evaluation metrics are aligned with human judgment, you can iterate quickly with automated feedback for each change.

One Change at a Time

Isolate the effect of each change. Run an evaluation after every modification. Use version comments to document what changed.

ALTER AGENT my_agent COMMIT
  COMMENT = 'Added explicit tool
  selection instructions';

Choosing the Orchestration LLM

Start with a powerful SOTA model (e.g., Claude Opus) to determine maximum performance. Then benchmark cheaper models against that ceiling. Pin a specific model for reproducibility — avoid auto.

Reading Evaluation Explanations

LLM judges produce explanations for each score. Use these to understand what went wrong and determine targeted fixes rather than guessing at improvements.

Goal Setting: Consistency Over Perfection

A score of 100% typically signals your dataset is too easy. An unstable score (80% → 65% → 90%) suggests the agent lacks consistency — add more explicit instructions or verified queries. A stable score is more meaningful than a high one.

What to Change (Investigation Signals)

  • Low answer correctness → improve instructions/tools
  • Low logical consistency → simplify system prompt
  • Low groundedness → improve search/retrieval
  • Low tool selection → better tool descriptions
  • Production failures → add those queries to eval set

  • Underlying data changes
  • Tool configuration drift

Deployment Strategies

  • Alias promotion — single command, zero client changes
  • Shadow testing — run candidate alongside production, compare offline
  • A/B split — cohort-based routing via app layer
  • Instant rollback — reassign alias to prior version

What to Monitor

  • Usage and adoption patterns
  • Latency percentiles (P50, P95, P99)
  • Token cost per conversation
  • Reliability (error rate)
  • Tool execution patterns
  • User feedback (thumbs up/down)
  • Conversation completion rate

      SNOWFLAKE.LOCAL.GET_AI_EVALUATION_DATA(

  ))
  THEN CALL SYSTEM$SEND_SNOWFLAKE_NOTIFICATION(...);

From Evaluations to Guardrails

Once LLM judges are aligned to expert judgment, extend their use beyond offline evaluation:

  • Offline monitoring — sample production traffic, score with judges, track trends
  • Real-time guardrails — distill critical judges into smaller, faster ML models
  • Feedback prioritization — focus review on negative feedback + low-scoring traces

Production failures become new evaluation dataset entries, completing the improvement cycle.

Key Takeaways

  • Evaluate the full reasoning chain, not just the final answer
  • Use the GPA framework: Goal, Plan, Action alignment
  • Start with real user queries — synthetic data is a fallback
  • Calibrate LLM judges to 80%+ correlation with human experts
  • One change at a time; evaluate after each change
  • Combine CI/CD gates with scheduled cadence testing

Getting Started

  • Step 1: Build 50-100 representative Q&A pairs from user logs
  • Step 2: Run your first evaluation with built-in metrics
  • Step 3: Set up agent versioning with aliases (dev/uat/prod)
  • Step 4: Add a custom metric for your domain
  • Step 5: Integrate evaluations into your CI/CD pipeline
  • Step 6: Set up production alerts and scheduled testing

Evaluation is not a one-time gate — it's a continuous improvement loop. Every production failure becomes a new test case. Every iteration builds on versioned, measurable progress.
