The Problem

Mutable = Risky

Without versioning, every edit to an agent immediately affects production users. One bad instruction change can degrade all responses.

No Rollback Path

If something breaks, you're scrambling to remember what the configuration looked like before. No snapshots, no history.

No Testing Gate

Changes go live without passing through UAT. You can't validate agent behavior against a test suite before deployment.

Blind in Production

Without monitoring, you don't know if your agent is hallucinating, selecting wrong tools, or degrading over time.

Cortex Agent Versioning solves all of these with a commit-based model that separates development from production.

The Versioning Model

Concept Mutability Purpose Example
Live Version Mutable Active development & iteration LIVE
Named Version Immutable Stable deployment snapshot VERSION$3
Alias Pointer Human-readable routing label production
Key insight: Named versions are immutable snapshots. Aliases are reassignable pointers. Your application targets aliases — you promote by moving the pointer, not changing code.

On Create

Agent automatically gets VERSION$1 (committed) + a LIVE version (mutable copy).

On Commit

LIVE is frozen into VERSION$N. A new LIVE version must be explicitly created to resume development.

-- Commit the live version to create an immutable snapshot
ALTER AGENT my_agent COMMIT
  COMMENT = 'Ready for UAT testing';

-- Resume development from the last committed version
ALTER AGENT my_agent ADD LIVE VERSION FROM LAST
  COMMENT = 'Starting next iteration';

Aliases & Shortcuts

Aliases

Human-readable labels you assign to versions. Reassign to redirect traffic without client changes.

-- Assign alias
ALTER AGENT my_agent
  MODIFY VERSION VERSION$3
  SET ALIAS = production;

-- Promote new version
ALTER AGENT my_agent
  MODIFY VERSION VERSION$4
  SET ALIAS = production;

CI/CD Integration

Git-Connected Workflow

  • Edit agent YAML in Git
  • Review via pull request
  • CI imports version from stage
  • Assign alias to deploy

Key Benefit

Bypasses the live version entirely. Changes are merged offline and imported as a new named version directly from Git.

-- Import version from a Git-connected stage after merge
ALTER AGENT my_agent ADD VERSION FROM @my_repo/tags/v2.1/agents/my_agent
  COMMENT = 'Automated deploy from CI pipeline';

-- Or create a brand new agent from a stage (infrastructure-as-code)
CREATE AGENT my_agent
  COMMENT = 'Deployed by CI pipeline'
  FROM @my_stage/agents/my_agent;
Tip: Use the LAST shortcut in CI scripts when you don't know the version number ahead of time.

A/B Testing Approaches

Application-Layer Routing

Assign two aliases (production + canary). Route a percentage of traffic to the canary in your app code. Correlate version with feedback/metrics.

Shadow Testing

Run both versions on the same input. Serve production response to the user, log the candidate response for offline comparison and evaluation.

Cohort-Based Split

Use user attributes (user ID hash, region, role) to deterministically route users to version A or B. Ensures consistent experience per user.

Note: Snowflake does not have native traffic splitting for agents. A/B testing is implemented at the application layer using versioned endpoints and aliases.

A/B Testing: Implementation

# Setup: assign aliases to the two versions under test
# ALTER AGENT my_agent MODIFY VERSION VERSION$3 SET ALIAS = production;
# ALTER AGENT my_agent MODIFY VERSION VERSION$4 SET ALIAS = canary;

import random
import hashlib

def get_agent_version(user_id, canary_pct=10):
    """Deterministic routing based on user ID."""
    bucket = int(hashlib.md5(user_id.encode()).hexdigest(), 16) % 100
    return "canary" if bucket < canary_pct else "production"

def call_agent(user_id, query):
    version = get_agent_version(user_id)

        f"/api/v2/databases/{db}/schemas/{schema}"

Key pattern: Always log which version served each request. This lets you correlate user feedback, evaluation scores, and latency with specific versions.

Production Monitoring

Conversation History

Full thread-level conversation logs stored automatically. View in Snowsight under AI & ML → Agents → Monitoring.

Execution Traces

Spans for LLM planning, tool execution (Search, Analyst, web), SQL execution, chart generation, and response generation.

Inputs & Outputs

Each span captures its inputs and outputs for debugging. See exactly what the agent planned, what tools returned, and how it responded.

User Feedback

Thumbs up/down ratings and free-text feedback captured per response. Use to identify degradation patterns.

Storage: All observability data is stored in SNOWFLAKE.LOCAL.AI_OBSERVABILITY_EVENTS. Query with the SNOWFLAKE.AI_OBSERVABILITY_READER role. Entries cannot be modified (append-only).

Agent Evaluations

Built-in Metrics

MetricType
Answer Correctness Ground truth
Logical Consistency Reference-free

Answer correctness compares agent output to expected answers. Logical consistency evaluates coherence across instructions, planning, and tool calls without ground truth.

Custom Metrics

Define domain-specific evaluation criteria using LLM-judged prompts:

  • Tone & brand adherence
  • Tool selection accuracy
  • Citation quality
  • Response completeness
Evaluation traces the full pipeline: planning, tool selection, execution results, and response generation. Identify exactly where quality degrades.

Rollback Strategy

-- One command to rollback: reassign the production alias
ALTER AGENT my_agent
  MODIFY VERSION VERSION$3 SET ALIAS = production;

-- All traffic immediately routes to the previous stable version
-- No client changes, no redeployment, no downtime

Why This Works

Named versions are immutable. VERSION$3 is exactly the same configuration that was working before. No drift, no surprises.

Best Practice

Always keep at least 2-3 previous named versions available. Only drop versions you're certain you'll never need to roll back to.

Next Steps

1. Set Up Aliases

Establish dev, uat, and production aliases on your existing agents. Update application code to target aliases instead of hardcoded versions.

2. Build Evaluation Suite

Create a ground-truth dataset of question/answer pairs. Define custom metrics for your domain. Run evaluations against UAT before promoting.

3. Implement A/B Routing

Add version routing logic to your application layer. Start with a 90/10 split. Log version per request for correlation with feedback.

4. Monitor & Iterate

Query AI_OBSERVABILITY_EVENTS for trace analysis. Set up alerts on feedback score degradation. Continuously refine based on evaluation results.

Remember: Aliases are your environment abstraction. Your app targets an alias — you promote and rollback by moving the pointer.
