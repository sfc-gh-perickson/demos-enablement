Cortex AI Observability:
Surface Identification & Cost Attribution

Know who's calling, from where, and what it costs — across every Cortex AI surface.

5+ Surfaces — MCP, REST, CoWork, Code, Agent API
Token-Level Granular cost data per model per request
Tag-Based Cost center grouping via user/agent tags
Real-Time 1–2 minute observability latency

Two parts: Surface identification (who's asking, from where) + Cost attribution (what does it cost, and who pays)

The Multi-Surface Challenge

Cortex AI is accessible from many entry points. Each generates usage that must be tracked and attributed.

MCP Clients

Claude Desktop, ChatGPT, Cursor, and other MCP-compatible clients calling Cortex Agents as tools.

REST API Direct

Programmatic access via /api/v2/cortex/agent:run and /api/v2/cortex/inference:complete.

CoWork / Intelligence

Snowflake's built-in conversational AI interface in Snowsight. Users interact naturally without writing code.

Agent Admin UI

The Snowsight agent playground for testing and iterating on agent configurations.

SQL Function Calls

SELECT SNOWFLAKE.CORTEX.AGENT(...) invoked inline within SQL queries and stored procedures.

Cortex Code CLI

The developer CLI that uses Cortex AI for code generation, analysis, and SQL authoring.

Without unified observability, adoption insights and cost management happen in silos. You can't answer "how much AI is my team consuming?" without correlating data from multiple views.

The Observability Landscape

Each surface writes to specific views in SNOWFLAKE.ACCOUNT_USAGE. Knowing which view to query is step one.

Surface Identification: Cortex Agents

CORTEX_AGENT_USAGE_HISTORY is the primary view for agent traffic. The METADATA column contains interaction_interface to identify the calling surface.

-- Identify which surfaces are calling your agents
SELECT
  METADATA:'interaction_interface'::STRING AS interface,
  AGENT_NAME,
  COUNT(*) AS requests,
  SUM(CREDITS_USED) AS total_credits
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_AGENT_USAGE_HISTORY
WHERE START_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY 1, 2
ORDER BY total_credits DESC;

external

MCP clients (Claude, ChatGPT, Cursor), programmatic REST API calls, and any non-Snowsight interface. This is the catch-all for API-driven access.

sql_function

Agent invoked via SNOWFLAKE.CORTEX.AGENT() SQL function within queries, stored procedures, or tasks.

agent_admin_ui

Snowsight's agent playground — the built-in testing interface where developers iterate on agent configurations.

microsoft_teams

Agents exposed via the Microsoft Teams integration. Tracks conversational AI usage from collaboration tools.

Key detail: MCP traffic (Claude Desktop, ChatGPT, etc.) and direct REST API calls both appear as external. There is no finer-grained distinction at the interaction_interface level today.

Surface Identification: CoWork & REST

Separate views capture usage from Snowflake Intelligence (CoWork) and direct REST API calls to LLM endpoints.

CoWork / Intelligence

-- CoWork usage by intelligence instance
SELECT
  SNOWFLAKE_INTELLIGENCE_NAME,
  USER_NAME,
  COUNT(*) AS conversations,
  SUM(CREDITS_USED) AS credits
FROM SNOWFLAKE.ACCOUNT_USAGE
  .SNOWFLAKE_INTELLIGENCE_USAGE_HISTORY
WHERE START_TIME >= DATEADD('day', -7,
  CURRENT_TIMESTAMP())
GROUP BY 1, 2;

Identifies traffic by SNOWFLAKE_INTELLIGENCE_NAME and SNOWFLAKE_INTELLIGENCE_ID. Each CoWork instance is a distinct object.

Direct REST API

-- REST API usage by model
SELECT
  MODEL_NAME,
  USER_NAME,
  COUNT(*) AS requests,
  SUM(TOKENS) AS total_tokens,
  SUM(CREDITS_USED) AS credits
FROM SNOWFLAKE.ACCOUNT_USAGE
  .CORTEX_REST_API_USAGE_HISTORY
WHERE START_TIME >= DATEADD('day', -7,
  CURRENT_TIMESTAMP())
GROUP BY 1, 2;

Captures direct CORTEX.COMPLETE(), CORTEX.EMBED(), and other LLM endpoint calls with MODEL_NAME and REQUEST_ID.

MCP Client Identification

Distinguishing between MCP clients requires a workaround today — the platform groups all external API access under one label.

Known limitation: MCP requests from Claude Desktop vs. ChatGPT vs. Cursor vs. other clients all appear as external in interaction_interface. There is no platform-native way to distinguish between MCP client types today.

Workaround: QUERY_TAG Pattern

-- Set a session-level query tag to identify the calling application
ALTER SESSION SET QUERY_TAG = '{"app":"my_mcp_client","client":"claude_desktop","team":"data-eng"}';

-- This tag propagates to QUERY_ATTRIBUTION_HISTORY
-- and can be parsed for attribution

Real-World Example: Cortex Code CLI

-- Cortex Code sets its own query tag automatically
SELECT
  QUERY_TAG,
  CREDITS_ATTRIBUTED_COMPUTE
FROM SNOWFLAKE.ORGANIZATION_USAGE.QUERY_ATTRIBUTION_HISTORY
WHERE QUERY_TAG LIKE '%cortex_code_cli%'
LIMIT 5;

-- Returns: {"app":"cortex_code_cli"}

Recommendation: If you control the MCP server or client integration, set QUERY_TAG as a JSON object at session start. This gives you client-level attribution via QUERY_ATTRIBUTION_HISTORY even without platform-native support.

Cost Attribution: Token-Level Granularity

The TOKENS_GRANULAR and CREDITS_GRANULAR VARIANT columns provide per-model, per-request cost breakdowns including cache economics.

-- Anatomy of TOKENS_GRANULAR (VARIANT column)
-- Each request contains a nested structure:
{
  "request_id": "01bb1234-...",
  "service_type": "cortex_agents",
  "model": "claude-3-5-sonnet",
  "tokens": {
    "input": 2450,
    "cache_read_input": 1800,
    "cache_write_input": 650,
    "output": 312
  }
}
-- Parse token-level costs per model from agent usage
SELECT
  AGENT_NAME,
  f.value:'model'::STRING AS model,
  SUM(f.value:'tokens':'input'::NUMBER) AS input_tokens,
  SUM(f.value:'tokens':'cache_read_input'::NUMBER) AS cache_hits,
  SUM(f.value:'tokens':'output'::NUMBER) AS output_tokens,
  SUM(g.value:'credits'::FLOAT) AS total_credits
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_AGENT_USAGE_HISTORY,
  LATERAL FLATTEN(TOKENS_GRANULAR) f,
  LATERAL FLATTEN(CREDITS_GRANULAR) g
WHERE f.value:'request_id' = g.value:'request_id'
  AND START_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY 1, 2;

Cache economics: cache_read_input tokens are significantly cheaper than fresh input tokens. Monitor your cache hit ratio — a high ratio means your prompt prefix caching is working effectively and reducing per-request cost.

Cost Attribution: Tag-Based Grouping

USER_TAGS and AGENT_TAGS arrays enable multi-level cost center attribution without modifying application code.

-- USER_TAGS and AGENT_TAGS are ARRAY columns
-- Tags are set at multiple levels and merged at query time:
--   ACCOUNT level:  ALTER ACCOUNT SET CORTEX_AGENT_USER_TAGS = [...]
--   USER level:     ALTER USER x SET CORTEX_AGENT_USER_TAGS = [...]
--   SCHEMA level:   ALTER SCHEMA SET CORTEX_AGENT_TAGS = [...]
--   AGENT level:    ALTER AGENT x SET CORTEX_AGENT_TAGS = [...]

-- Extract cost by tag (cost center attribution)
SELECT
  t.value::STRING AS cost_center_tag,
  AGENT_NAME,
  COUNT(*) AS requests,
  SUM(CREDITS_USED) AS total_credits
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_AGENT_USAGE_HISTORY,
  LATERAL FLATTEN(USER_TAGS) t
WHERE START_TIME >= DATEADD('day', -30, CURRENT_TIMESTAMP())
GROUP BY 1, 2
ORDER BY total_credits DESC;

Multi-Level Tagging

LevelScopeExample
AccountAll users in account["dept:engineering"]
UserIndividual user["team:platform","role:admin"]
SchemaAll agents in schema["project:analytics"]
AgentSpecific agent["app:sales-copilot"]

Attribution Strategy

  • USER_TAGS → Who triggered it (chargeback to team)
  • AGENT_TAGS → What product consumed it (cost to project)
  • Combine both for full cost center matrix
  • Tags are inherited: account → user, schema → agent

Building a Unified Cost View

No single view captures all Cortex AI usage. Build a normalized UNION ALL to create a single pane of glass across all surfaces.

-- Unified Cortex AI usage view across all surfaces
CREATE OR REPLACE VIEW analytics.cortex_unified_usage AS

-- Cortex Agents (MCP, REST, Snowsight, SQL, Teams)
SELECT
  'cortex_agent' AS surface,
  USER_NAME,
  AGENT_NAME,
  METADATA:'interaction_interface'::STRING AS interface,
  TOKENS_USED AS tokens,
  CREDITS_USED AS credits,
  START_TIME AS ts
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_AGENT_USAGE_HISTORY

UNION ALL

-- CoWork / Snowflake Intelligence
SELECT
  'cowork' AS surface,
  USER_NAME,
  SNOWFLAKE_INTELLIGENCE_NAME AS agent_name,
  'snowsight' AS interface,
  TOKENS_USED AS tokens,
  CREDITS_USED AS credits,
  START_TIME AS ts
FROM SNOWFLAKE.ACCOUNT_USAGE.SNOWFLAKE_INTELLIGENCE_USAGE_HISTORY

UNION ALL

-- Cortex Code CLI
SELECT
  'cortex_code' AS surface,
  USER_NAME,
  NULL AS agent_name,
  'cli' AS interface,
  TOKENS AS tokens,
  CREDITS_USED AS credits,
  START_TIME AS ts
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_CODE_CLI_USAGE_HISTORY;
-- Query the unified view: top consumers last 7 days
SELECT
  surface,
  USER_NAME,
  COUNT(*) AS requests,
  SUM(tokens) AS total_tokens,
  SUM(credits) AS total_credits
FROM analytics.cortex_unified_usage
WHERE ts >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY 1, 2
ORDER BY total_credits DESC
LIMIT 20;

Resource Budgets for AI

Proactive governance via budgets prevents runaway costs. Different surfaces support different budget mechanisms.

FeatureResource BudgetShared BudgetCredit LimitsNotes
Cortex Agents Yes Yes — Per-agent or per-schema budgets
CoWork / Intelligence Yes Yes — Per-intelligence-object budgets
Cortex Code CLI — Yes Yes Account-level credit limits
AI Functions (Complete, etc.) — Yes — Shared budget only
Cortex Search Yes Yes — Per-service budgets

Threshold Alerts

Budgets support notification thresholds (e.g., alert at 75%, 90%, 100%) via notification integrations (email, Slack, PagerDuty).

-- Create a resource budget for an agent
CREATE RESOURCE BUDGET sales_agent_budget
  FOR CORTEX_AGENT my_db.my_schema.sales_agent
  CREDIT_LIMIT = 100
  FREQUENCY = 'MONTHLY';

Automated Actions

  • Notify — alert admins when thresholds are crossed
  • Suspend — automatically block new requests at 100%
  • Carry-over — unused budget rolls to next period (shared budgets)

Resource budgets enforce hard limits. Shared budgets provide pool-based governance with softer controls.

Query-Level Attribution

QUERY_ATTRIBUTION_HISTORY captures warehouse compute costs for queries generated by agents — the "downstream" cost of AI-generated SQL.

-- Find warehouse costs generated by agent-driven queries
SELECT
  PARSE_JSON(QUERY_TAG):'app'::STRING AS app,
  WAREHOUSE_NAME,
  COUNT(*) AS queries,
  SUM(CREDITS_ATTRIBUTED_COMPUTE) AS compute_credits,
  AVG(ELAPSED_TIME_MS) AS avg_latency_ms
FROM SNOWFLAKE.ORGANIZATION_USAGE.QUERY_ATTRIBUTION_HISTORY
WHERE QUERY_TAG IS NOT NULL
  AND TRY_PARSE_JSON(QUERY_TAG) IS NOT NULL
  AND START_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY 1, 2
ORDER BY compute_credits DESC;

Linking AI Cost to Compute Cost

The full cost of an AI interaction is:

  • AI tokens (from CORTEX_AGENT_USAGE_HISTORY)
  • + Warehouse compute (from QUERY_ATTRIBUTION_HISTORY)
  • + Storage (Cortex Search indexes, if applicable)

Link them via QUERY_TAG JSON or correlation on user + time window.

QUERY_TAG as the Link

Cortex services automatically set QUERY_TAG on queries they generate. Parse the JSON to identify the source:

-- Example QUERY_TAG values:
{"app":"cortex_code_cli"}
{"app":"cortex_agent",
 "agent":"sales_agent"}
{"app":"my_mcp_client",
 "client":"claude_desktop"}

Summary

  • Use interaction_interface for surface routing — identifies MCP, SQL, UI, and Teams traffic
  • Parse TOKENS_GRANULAR for per-model, per-request cost breakdowns with cache visibility
  • Tag users and agents for cost center attribution across teams and projects
  • Build unified views via UNION ALL across surface-specific usage tables
  • Set resource budgets for proactive governance with threshold alerts

Getting Started

  • Step 1: Grant IMPORTED PRIVILEGES on SNOWFLAKE DB to your monitoring role
  • Step 2: Query CORTEX_AGENT_USAGE_HISTORY to understand your current surface mix
  • Step 3: Set up USER_TAGS for cost center grouping
  • Step 4: Create the unified usage view
  • Step 5: Configure resource budgets on high-traffic agents
  • Step 6: Build a Streamlit dashboard for ongoing visibility

Feature to watch: Finer-grained MCP client identification is a known gap. Today all external API access is one bucket. Expect future interaction_interface values or metadata fields that distinguish between MCP client types (Claude, ChatGPT, Cursor, custom).

Observability is not optional for production AI. Surface identification answers "who's using it?" Cost attribution answers "what does it cost?" Together they enable informed governance decisions.
