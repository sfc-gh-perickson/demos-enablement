Problem Statement

The data ingestion challenge at scale

Format Chaos

Departments submit CSVs from travel systems, expense platforms, vendor portals. Column headers vary wildly between customers and even between months from the same customer.

100s of Sources

Each with different source systems. Monthly recurring uploads. 100K records at the high end. Can't afford per-row LLM calls — column mapping is file-level, not row-level.

Multiple Templates

Data must conform to exact canonical schemas (mileage, purchases, invoices, payroll, etc.). System must figure out WHICH template matches, not just map columns.

Reliability Required

Finance-facing pipeline. Can't hallucinate mappings or lose data. Must be deterministic at execution time. Human approval mandatory before any data load.

3 / 15

Solution Overview

Three-layer approach: smart orchestration, one-time AI, deterministic execution

1

Cortex Agent — Orchestration + User Interaction

Snowflake CoWork chat interface. Routes user intent to tools, presents results, enforces human-in-the-loop approval. Never writes SQL directly.

2

AI_COMPLETE — One-Time Mapping Proposal

Called exactly once per NEW file format (cache miss). Proposes which template matches and how to map each column. ~950 tokens mapping + ~900/entity resolution column. Cached thereafter.

3

Deterministic SP — At-Scale Execution

No LLM touches data rows. SP builds COPY INTO from an operations enum. 100K rows load in seconds via a single deterministic SQL statement. Zero variability.

Key insight: The LLM decides HOW to map (once). The SP executes the mapping (every time). No tokens per row, ever.

Stored Procedures & UDFs

All database objects powering the pipeline

Object Type What It Does
LIST_STAGED_FILES() UDF Reads DIRECTORY(@UPLOAD_STAGE), returns file list
GET_TARGET_SCHEMAS() UDF Queries INFORMATION_SCHEMA.COLUMNS, returns canonical table schemas
SP_PROFILE_STAGED_FILE(path) SP INFER_SCHEMA + sample 20 rows. Builds per-column stats: cardinality, null_rate, samples, types. Zero tokens.
PROFILE_FILE(path) SP Wrapper — calls SP_PROFILE_STAGED_FILE, formats as human-readable text for agent presentation
PROPOSE_MAPPING(profile_text) SP First checks MAPPING_CONFIGS cache (SHA256 hash). If miss: calls AI_COMPLETE('claude-4-sonnet') with schema + profile. Returns JSON mapping.
EXECUTE_MAPPING(json, path) SP Calls SP_BUILD_AND_EXECUTE_COPY_INTO, saves config to cache on success
SP_BUILD_AND_EXECUTE_COPY_INTO(...) SP Builds deterministic COPY INTO from operations enum. Sets DATE_INPUT_FORMAT=AUTO. Executes with FORCE=TRUE, ON_ERROR=CONTINUE.

Design principle: The agent NEVER writes SQL. It calls tools → tools return structured data → agent presents to user. AI_COMPLETE is called inside PROPOSE_MAPPING only, and only on cache miss.

Workflow: Discovery & Profiling

Steps 1–3: File discovery, profiling, and mapping proposal

1

File Discovery

Agent calls list_staged_files(). UDF reads DIRECTORY(@UPLOAD_STAGE) and returns available CSVs. User picks which file to map.

2

Profiling (Zero Tokens)

Agent calls profile_file(filename). SP uses INFER_SCHEMA (no LLM). Returns: column count, row count, per-column metadata — 5 sample values, cardinality, null rate, inferred type. Pure SQL execution.

3

Cache Check + Mapping Proposal

PROPOSE_MAPPING computes SHA256(sorted lowercase column names). Queries MAPPING_CONFIGS. If hit: returns stored mapping instantly (0 tokens). If miss: calls AI_COMPLETE with target schemas from INFORMATION_SCHEMA + profile. Returns JSON with target_table, mappings, ignored columns, rationale.

-- Example profile output the agent sees: -- 9 columns, 166 rows -- Vendor (TEXT): 16 distinct, 0% null, samples: ["Staples", "Amazon Web Services", ...] -- Amt (TEXT): 20 distinct, 2% null, samples: ["$142.67", "~2400", "$534"] -- When (TEXT): 83 distinct, 0% null, samples: ["2025-01-15", "Jan 21, 2025", "02/14/2025"]

Workflow: Approval & Execution

Steps 4–5: Human gate and deterministic load

4

Human Approval — NEVER Skipped

Agent presents proposed mapping as a table: Source → Target → Operation. User reviews, can modify, then explicitly confirms. Enforced in agent's system prompt — cannot proceed without approval.

5

Execution (Zero Tokens)

SP builds COPY INTO deterministically from operation enum. Sets DATE_INPUT_FORMAT = 'AUTO' (handles all date formats). FORCE=TRUE (allows reload). ON_ERROR=CONTINUE (skips bad rows). Reports: rows_parsed, rows_loaded, rows_rejected, first_error.

-- Example mapping JSON the agent presents for approval: { "target_table": "PURCHASE_EXPENSES", "mappings": [ {"source": "Vendor", "dest": "EXPENSE_CATEGORY", "operation": "TRIM"}, {"source": "Amt", "dest": "AMOUNT", "operation": "NUMERIC_STRIP_UNITS"}, {"source": "When", "dest": "TRANSACTION_DATE", "operation": "TO_DATE"} ], "ignored": ["Misc", "Approved?"] } -- After approval, SP generates and executes: COPY INTO ACME_FINANCE.INGESTION.PURCHASE_EXPENSES (EXPENSE_CATEGORY, AMOUNT, ...) FROM (SELECT NULLIF(TRIM($1),''), TRY_TO_NUMBER(REGEXP_REPLACE(...)), ... FROM @UPLOAD_STAGE/sample_file.csv) FILE_FORMAT = (TYPE=CSV SKIP_HEADER=1 FIELD_OPTIONALLY_ENCLOSED_BY='"') ON_ERROR = CONTINUE FORCE = TRUE;

On success: mapping config saved to MAPPING_CONFIGS automatically. Same format next month = instant cache hit, zero questions.

Operations Enum

Transform primitives — LLM picks the operation, SP generates exact SQL

Operation Generated SQL Example Input → Output
TRIM NULLIF(TRIM($N), '') "  hello  " → "hello"
NUMERIC_STRIP_UNITS TRY_TO_NUMBER(REGEXP_REPLACE(REPLACE($N,'~',''),'[^0-9.]','')) "$304" → 304, "~152" → 152
RESOLVE_ENTITY CASE WHEN $N LIKE '%km%' THEN 'km' ELSE 'USD' END "$304" → "USD"
TO_DATE TRY_TO_DATE(TRIM($N)) "Sep 21, 2025" → 2025-09-21
TO_DATE_START TRY_TO_DATE(SPLIT_PART(REGEXP_REPLACE($N,...), ' to ', 1)) "05/09/2025 to 05/13/2025" → 2025-05-09
TO_DATE_END COALESCE(TRY_TO_DATE(SPLIT_PART(..., 2)), TRY_TO_DATE(SPLIT_PART(..., 1))) "05/09/2025 to 05/13/2025" → 2025-05-13
RESOLVE_ENTITY CASE WHEN $N LIKE '%Software%' THEN 'Software' ELSE 'Office Supplies' END "Office Depot" → "Office Supplies"
TO_NUMBER TRY_TO_NUMBER($N) "42" → 42
DIRECT $N Pass-through, no transform

One source → multiple targets: A single column like "trip period" can map to BOTH TRANSACTION_DATE (TO_DATE_START) and DUE_DATE (TO_DATE_END) with different operations. Adding new operations = one CASE branch in the SP.

Mapping Cache Deep Dive

SHA256 hash → instant reuse across filenames and months

1

Hash Computation

sorted(lowercase(column_names)).join('|') → SHA256. Same columns in different order = same hash. Different filename = same hash. Only the column signature matters.

2

Storage

MAPPING_CONFIGS table: SOURCE_COLUMN_HASH, COLUMN_MAP (JSON), TARGET_TABLE, TIMES_USED counter, CREATED_AT timestamp.

3

Lookup

WHERE SOURCE_COLUMN_HASH = :hash ORDER BY CREATED_AT DESC LIMIT 1. On hit: returns stored mapping, increments TIMES_USED, zero LLM call.

4

Save on Success

New configs saved automatically by EXECUTE_MAPPING after successful COPY INTO. Only approved + successfully executed mappings are persisted.

Benchmarked: Cross-file reuse

In testing, sample_invoices_03_chaotic.csv automatically reused the cache from expenses_chaotic.csv because they share the same column signature — despite having different filenames and data. Customer uploads "fleet_jan_2026.csv" (cache miss → ~950 tokens). Next month: "fleet_feb_2026.csv" with same columns → instant cache hit, 0 tokens, 0 user questions.

Date Handling Deep Dive

The hardest problem solved — mixed formats in a single column

The Problem

COPY INTO doesn't reliably support TRY_TO_DATE with explicit format strings when a single column contains mixed date formats (MM/DD/YYYY, YYYY-MM-DD, Mon DD YYYY all in the same file).

The Solution

ALTER SESSION SET DATE_INPUT_FORMAT = 'AUTO' before COPY INTO. Snowflake auto-detects format per row. Set at session level inside SP before every execution.

Formats Handled Automatically

Input Format Example Parsed As
MM/DD/YYYY01/15/20252025-01-15
YYYY-MM-DD2025-01-152025-01-15
DD/MM/YYYY15/01/20252025-01-15
Mon DD, YYYYJan 15, 20252025-01-15
DD-Mon-YY15-Jan-252025-01-15

Date Ranges

-- Input: "05/09/2025 to 05/13/2025" or "Jan 1 – Mar 31, 2025" -- Step 1: REGEXP_REPLACE normalizes separators (–, -, to) → ' to ' -- Step 2: SPLIT_PART extracts start (position 1) and end (position 2) -- Step 3: TRY_TO_DATE with AUTO format parses each half -- Fallback: TO_DATE_END uses COALESCE to fall back to start date if end is empty

Known limitation: DD/MM/YYYY vs MM/DD/YYYY is ambiguous for dates like 01/02/2025. AUTO uses Snowflake's US-format bias. ON_ERROR=CONTINUE as safety net for truly unparseable values.
