The Problem

ML teams waste months rebuilding features across environments while silently introducing training/serving skew.

Feature Drift

Training features ≠ serving features. Subtle differences in logic between batch pipelines and real-time services cause model degradation that's nearly impossible to detect.

Pipeline Duplication

The same feature logic reimplemented in Spark for training, Python for serving, and SQL for dashboards — each with its own bugs and versioning.

No Governance

Who changed this feature? When? What models depend on it? Without a centralized registry, feature changes silently break downstream consumers.

Temporal Leakage

Future data leaking into training sets produces artificially high accuracy that evaporates in production. Naive joins don't respect event time.

Offline Store — Dynamic Tables

Declarative SQL transformations with configurable target_lag. Snowflake handles incremental refresh, dependency ordering, and compute scaling automatically.

Online Store — Hybrid Tables

Row-level CRUD with sub-second point lookups. Automatic sync from offline store via incremental pipelines. Built for real-time serving at scale.

Entities & Feature Views

Logical building blocks: Entities define the grain, Feature Views define the features computed at that grain.

Entities

from snowflake.ml.feature_store import Entity # Define the grain of your features customer = Entity( name="CUSTOMER", join_keys=["CUSTOMER_ID"] ) product = Entity( name="PRODUCT", join_keys=["PRODUCT_ID"] ) fs.register_entity(customer) fs.register_entity(product)

Feature Views

from snowflake.ml.feature_store import FeatureView # Feature view = entity + features + logic customer_fv = FeatureView( name="CUSTOMER_PURCHASE_FEATURES", entities=[customer], feature_df=customer_features_df, timestamp_col="EVENT_TIMESTAMP", refresh_freq="60 minutes", desc="Customer purchase behavior" ) fs.register_feature_view( feature_view=customer_fv, version="v1" )

Feature Engineering

Register raw features directly from source tables or build engineered features with Snowpark DataFrame transforms.

Raw Feature View — Direct from Source

# Raw features: select columns directly from source tables raw_df = session.sql(""" SELECT CUSTOMER_ID, TOTAL_LIFETIME_SPEND, ACCOUNT_AGE_DAYS, LOYALTY_TIER, EVENT_TIMESTAMP FROM ECOMMERCE.CUSTOMERS """) raw_fv = FeatureView( name="CUSTOMER_RAW_FEATURES", entities=[customer], feature_df=raw_df, timestamp_col="EVENT_TIMESTAMP" )

Engineered Feature View — Snowpark Transforms

# Engineered features: windowed aggregations via Snowpark from snowflake.snowpark import functions as F from snowflake.snowpark.window import Window orders = session.table("ECOMMERCE.ORDERS") win_7d = Window.partition_by("CUSTOMER_ID").order_by("ORDER_DATE").range_between(-7*86400, 0) engineered_df = orders.group_by("CUSTOMER_ID").agg( F.count("ORDER_ID").alias("ORDERS_7D"), F.avg("ORDER_TOTAL").alias("AVG_ORDER_VALUE_7D"), F.count_distinct("PRODUCT_CATEGORY").alias("UNIQUE_CATEGORIES_7D"), F.max("ORDER_DATE").alias("EVENT_TIMESTAMP") ) engineered_fv = FeatureView( name="CUSTOMER_BEHAVIOR_7D", entities=[customer], feature_df=engineered_df, timestamp_col="EVENT_TIMESTAMP", refresh_freq="30 minutes" )

Point-in-Time Correctness

The feature store performs temporal joins to ensure training data only uses features that were available at prediction time — preventing data leakage.

❌ Naive Join (Data Leakage)

  • JOIN ON customer_id only
  • Training sees future feature values
  • Artificially high offline metrics
  • Model fails in production
vs

✓ Point-in-Time Join

  • JOIN ON customer_id AND timestamp ≤ event
  • Only features known at prediction time
  • Honest offline metrics
  • Production matches training

Spine-Based Temporal Join

Spine (entity_id + timestamp)
+

→
PIT-Correct Dataset

For each spine row, the feature store finds the most recent feature value WHERE feature.timestamp ≤ spine.timestamp

Dataset Generation

Generate reproducible, point-in-time correct training datasets from registered feature views with a single API call.

# 1. Build the spine: entities + timestamps for training events spine_df = session.sql(""" SELECT CUSTOMER_ID, PURCHASE_TIMESTAMP AS SPINE_TIMESTAMP, DID_CONVERT AS LABEL FROM ECOMMERCE.TRAINING_EVENTS WHERE PURCHASE_TIMESTAMP BETWEEN '2024-01-01' AND '2024-06-30' """) # 2. Retrieve registered feature views customer_fv = fs.get_feature_view("CUSTOMER_PURCHASE_FEATURES", "v1") behavior_fv = fs.get_feature_view("CUSTOMER_BEHAVIOR_7D", "v1") # 3. Generate PIT-correct training set training_dataset = fs.generate_training_set( spine_df=spine_df, features=[customer_fv, behavior_fv], spine_timestamp_col="SPINE_TIMESTAMP", spine_label_cols=["LABEL"] ) # 4. Use directly for model training train_df = training_dataset.to_pandas()

Reproducibility Guarantee

The same spine + feature view versions always produce the same dataset. Feature views are versioned and immutable — change the logic, register a new version. Prior training runs remain reproducible.

Online Feature Store

Enable real-time feature serving with a single configuration flag. Backed by Hybrid Tables with configurable sync latency.

from snowflake.ml.feature_store import FeatureView, OnlineConfig # Enable online serving with target_lag customer_fv = FeatureView( name="CUSTOMER_REALTIME_FEATURES", entities=[customer], feature_df=realtime_features_df, timestamp_col="EVENT_TIMESTAMP", refresh_freq="5 minutes", online_config=OnlineConfig( enable=True, target_lag="30 seconds" ) ) fs.register_feature_view(feature_view=customer_fv, version="v1")

How It Works

When online_config is enabled, Snowflake materializes the feature view into a Hybrid Table optimized for key-value lookups. A background process syncs changes from the offline Dynamic Table to the online Hybrid Table within the specified target_lag window.

Real-Time Serving

Retrieve features from the online store for real-time inference with sub-second latency.

from snowflake.ml.feature_store import StoreType # Retrieve feature view customer_fv = fs.get_feature_view("CUSTOMER_REALTIME_FEATURES", "v1") # Read from online store (sub-second lookup) online_features = fs.read_feature_view( feature_view=customer_fv, entity_rows=session.create_dataframe( [("CUST_12345",)], schema=["CUSTOMER_ID"] ), store_type=StoreType.ONLINE ) # Use features for real-time scoring prediction = model.predict(online_features)

Model Integration

Bind feature views to model services — features are automatically looked up at inference time using only the entity key.

from snowflake.ml.registry import Registry reg = Registry(session=session) # Log the model with feature store lineage model_ref = reg.log_model( model=trained_model, model_name="product_recommender", version_name="v1", sample_input_data=training_features ) # Deploy as a service with auto feature lookup customer_fv = fs.get_feature_view("CUSTOMER_REALTIME_FEATURES", "v1") product_fv = fs.get_feature_view("PRODUCT_EMBEDDINGS", "v1") model_ref.create_service( service_name="recommendation_service", service_compute_pool="ML_INFERENCE_POOL", feature_sources_per_function={ "predict": [customer_fv, product_fv] } )

Zero-Feature Payloads

Callers send only entity keys (e.g., customer_id). The service automatically fetches all required features from the online store, ensuring consistency and eliminating the need for client-side feature construction.

Refresh & Monitoring

Dynamic Table-powered refresh with full observability — incremental by default, with monitoring and cost tracking built in.

Aspect Incremental Refresh Full Refresh

Compute Cost Low — processes only deltas High — reprocesses all data

Governance & Discovery

Enterprise-grade access control, lineage tracking, and feature discoverability built on Snowflake's governance layer.

RBAC Integration

Feature views inherit Snowflake's role-based access control. Grant SELECT on specific feature views to specific roles — no separate permission system to manage.

Lineage Tracking

Full lineage from source tables through feature views to models. Understand exactly which source columns feed which features and which models consume them.

Feature Discovery

Search and browse registered features across the organization. Find existing features before building new ones — avoid redundant computation.

Tags & Metadata

Apply Snowflake object tags for data classification, PII tracking, and organizational taxonomy. Features are first-class governed objects.

Cost Optimization

Use refresh_freq to control compute costs. High-frequency for real-time features (minutes), low-frequency for slowly-changing features (hours/days). Only online-enabled views incur Hybrid Table costs.

Feature Reuse

Register once, consume everywhere. Multiple models share the same feature views — no redundant computation. New models get existing features instantly.

Version Management

Register new versions for breaking changes. Old versions remain available for existing models. Migrate consumers gradually without coordinated deployments.
