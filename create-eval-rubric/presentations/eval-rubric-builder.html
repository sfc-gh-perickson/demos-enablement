Why agent evaluation stalls

The gap between a demo and production is trust. Most teams have no fixed dataset and no trusted metric, so every change is a guess.

No real questions

Teams jump from "talk to your data" to tools. The eval set is synthetic and misses what users actually ask.

No ground truth

Answers are judged by eye, and relative dates ("last week") make any stored answer stale.

Generic metrics

Off-the-shelf checks miss the domain failures that matter: net vs gross, data scope, policy accuracy.

Untrusted judges

LLM judges nobody checked against humans, scored on a different scale from the built-in metrics.

Step 1: a maker/checker scoping interview

The agent drafts from evidence, the user reviews and corrects. Nothing goes into the spec until the user confirms it.

Vision — "what should change for users?"
Personas — who, literacy, stakes, success signal
Questions — what they actually ask, by category
Tools & rules — definitions, boundaries, refusals
Agent spec — confirmed intake
Round A · ask

Vision & agent

One question set: business vision, agent under test, what it must never do. Then a silent evidence pass over the agent, semantic views and logs.

Round B · draft → review

Persona cards

2–4 drafted cards, each tagged with its evidence. Accept, edit, drop, or add one the agent missed.

Round C · draft → review

Questions & taxonomy

5–10 questions per persona in their words, plus "what did you ask your analyst last week?" Fill empty persona × category cells.

Round D · draft → review

Rules & boundaries

Definitions, out-of-scope with refusal wording, missing fields, format rules from literacy, pass criteria.

Persona cards and the question taxonomy

A persona's success signal is the north-star metric. A regional manager doesn't care about SQL correctness; they care that the number matches their analyst's.

Persona card (example: regional sales lead)

  • Decisions: territory allocation, quota
  • Literacy: reads dashboards, doesn't write SQL
  • Workflow: asks the analyst team, 2-day turnaround
  • Frequency: 5–10 questions / week
  • Data scope: own region only (row access policy)
  • Success signal: "I got the answer without filing a ticket"

Two tiers of metrics

Tier A needs ground truth and runs on the curated set. Tier B is reference-free, so once calibrated it can score any question, including production traffic.

Tier A · ground truth

Curated dataset only

  • answer_correctness (built-in)
  • tool_selection_accuracy, tool_execution_accuracy (built-in)
  • logical_consistency (built-in, reference-free)
  • business_rules, efficiency (custom)
Tier B · reference-free

Any question, including production logs

  • answer_correctness_rf, tool_selection_rf, tool_execution_rf
  • groundedness, business_rules_rf, date_interpretation
  • scope_refusal, persona_fit, brand_format, efficiency_rf
  • Only frozen (calibrated) judges go into configs
One judge model: every judge, calibration function and studio optimization uses the same judge_model (claude-sonnet-4-6). Optimization tunes the prompt only, never the model.

One scoring scale, matched to the built-in metrics

Built-in agent metrics report a normalized score from 0 to 1. Every custom judge uses the same scale and five written bands, so built-in and custom columns compare directly.

0
two or more criteria fail, or a fabricated number
0.25
one criterion clearly fails
0.5
one criterion partly missed
0.75
all hold, one cosmetic issue
1
every criterion holds
low  [0, 0.4)
medium  [0.4, 0.7]
high  (0.7, 1]

Built-ins pinned to v3

The v3 judge is the same model as the custom judges, and pinning keeps scores comparable across runs.

Same bands everywhere

Judges, human labels, calibration kappa and the studio agreement metric all use the same five bands.

Lint enforces it

A judge off this scale, or ranges that don't span 0–1, fails preflight.

Business and persona metrics, when they're needed

Generic judges cover generic quality. The skill drafts dedicated metrics when a persona or rule warrants one; the user accepts, edits or drops each.

Persona

Success signal not covered

finance_lead_board_ready: a one-line takeaway with metric, value and as-of date, ready for the board deck.

Persona

Restricted data scope

category_manager_scope: every figure is for the user's own category; cross-category asks are declined.

Business

Costliest definition

net_vs_gross: net unless gross is asked, always labelled, cancelled and test orders excluded.

Business

High-cost category

arr_as_of_date or a policy safety metric: one stated date, never summed across periods; cite or decline.

Keep it sharp: 2–4 custom metrics beat many vague ones, because each Tier B metric needs its own calibration. Persona- or category-scoped metrics score 1 with an N/A: reason elsewhere; filter those rows when reading averages.

Calibrating judges against humans

A Tier B judge is trusted only after it agrees with human raters on a holdout set. Then it's frozen and versioned.

1 · Collect

20–50 responses per judge

From a pilot eval run or observability logs; oversample high-cost categories and known failures.

2 · Label

Humans score the bands

Two raters where possible; check rater-vs-rater agreement first.

3 · Optimize

AI Function Studio

Baseline evaluation, then prompt-only optimization on train, judge model fixed.

4 · Freeze

Pass the gate

Weighted kappa ≥ 0.6 and exact-band agreement ≥ 0.8 on holdout, then judges/<metric>@vN.md.

Re-calibrate when the agent instructions, semantic view, tools or judge model change. Plan a ~10% human spot check on each production scoring batch.

Outputs and guardrails

Everything lands in a per-customer workshop directory, is versioned, and passes preflight lint before it touches Snowflake.

Artifacts

  • intake.yaml, questions.csv
  • dataset_v<N>.csv + review Sheet
  • judges/*.md, calibration_report.md
  • dataset.sql, eval_config.yaml, spec.md

Hard rules

  • Literal values in ground truth, never placeholders
  • Relative dates pinned for ground truth
  • Datasets and judges versioned, never edited in place
  • Only frozen Tier B judges in configs

Lint catches

  • Unconfirmed persona drafts, missing success signals
  • Empty taxonomy categories, coverage gaps
  • Judges off the 0–1 scale
  • Stale dates, near-duplicate questions

Next steps

Start with one agent and one persona-rich use case; the dataset and judges then carry through optimization, release and production.

Run a workshop

Pick a live Cortex Agent, invite 2–3 persona owners, and run Steps 1–5 onsite to leave with a reviewed dataset and signed-off metrics.

Calibrate and gate

Calibrate the Tier B and custom judges, then use the eval config as the merge gate for every agent change.

Optimize

Hand the dataset and config to agent-pareto-lab to compare models, prompts and tools on cost vs quality.

Close the loop

Score production logs with frozen judges on a schedule; turn low scores and rephrases into new eval cases.
