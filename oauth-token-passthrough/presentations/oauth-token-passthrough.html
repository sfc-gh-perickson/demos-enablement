OAuth Token Passthrough:
Per-User Identity for Cortex Agents

Pass an Entra ID token from your application through to Snowflake — the agent runs as the authenticated user, not a shared service account.

Per-User Agent runs with caller's privileges
No Secrets Token-based — no password storage
JWT Standard OAuth 2.0 / OIDC flow
Audit True user identity in query history

Core pattern: Your application obtains an OAuth token from Entra ID on behalf of the user, then passes it as a Bearer token to the Cortex Agent REST API. Snowflake validates the JWT via an External OAuth security integration, maps it to a Snowflake user, and the agent session runs with that user's roles and privileges.

Docs: External OAuth

The Problem

Why a shared service account breaks identity, auditability, and least-privilege.

Lost Identity

With a shared service account, all agent queries appear as the same user in QUERY_HISTORY. You can't tell who asked what or attribute costs to individuals.

Over-Privileged

The service account needs access to all data any user might query. Every user effectively has the union of all privileges — violating least-privilege.

Compliance Gap

Regulations (GDPR, SOX, HIPAA) require knowing who accessed data. A shared account makes individual access attribution impossible without application-layer workarounds.

Session Attributes Aren't Auth

Multi-tenancy session attributes provide authorization boundaries, but they don't solve authentication. You still need to prove the user is who they claim to be.

Token passthrough solves authentication. Each API call proves the caller's identity with a cryptographically signed token. Snowflake maps that token to a real user — giving you true per-user audit trails, privilege enforcement, and accountability.

What Snowflake Validates

  • JWT signature (via JWKS endpoint)
  • Issuer matches Entra ID tenant
  • Audience matches your app registration
  • Token not expired (exp claim)
  • Required scopes present

What Snowflake Does NOT Do

  • Does not contact Entra ID at runtime (offline validation)
  • Does not store the token
  • Does not manage user passwords
  • Does not handle token refresh — your app does

External OAuth Security Integration

The Snowflake object that tells the platform how to validate Entra ID tokens.

-- Create the External OAuth security integration for Entra ID
CREATE OR REPLACE SECURITY INTEGRATION entra_oauth_int
  TYPE = EXTERNAL_OAUTH
  ENABLED = TRUE
  EXTERNAL_OAUTH_TYPE = AZURE
  EXTERNAL_OAUTH_ISSUER = 'https://sts.windows.net/<your-tenant-id>/'
  EXTERNAL_OAUTH_JWS_KEYS_URL = 'https://login.microsoftonline.com/<your-tenant-id>/discovery/v2.0/keys'
  EXTERNAL_OAUTH_AUDIENCE_LIST = ('https://<your-snowflake-account>.snowflakecomputing.com')
  EXTERNAL_OAUTH_TOKEN_USER_MAPPING_CLAIM = 'upn'
  EXTERNAL_OAUTH_SNOWFLAKE_USER_MAPPING_ATTRIBUTE = 'login_name'
  EXTERNAL_OAUTH_ANY_ROLE_MODE = 'ENABLE';

Issuer & Keys

The issuer URL identifies your Entra ID tenant. The JWS keys URL provides the public keys Snowflake uses to verify JWT signatures — no shared secrets needed.

Audience

Must match the aud claim in the token. This is the app registration's Application ID URI or your Snowflake account URL. Mismatches cause immediate rejection.

User Mapping

Maps the upn (User Principal Name) claim from the JWT to a Snowflake user's login_name. This is the identity bridge between Entra ID and Snowflake.

Critical: The user mapping claim (upn or email) must exactly match the login_name of a Snowflake user. If no match is found, authentication fails with "User not found" — this is by design (no implicit user creation).

User Mapping

Bridging Entra ID identities to Snowflake users via login_name.

-- Create a Snowflake user mapped to an Entra ID identity
CREATE OR REPLACE USER alice_smith
  LOGIN_NAME = 'alice.smith@contoso.com'
  DISPLAY_NAME = 'Alice Smith'
  DEFAULT_ROLE = ANALYST_ROLE
  DEFAULT_WAREHOUSE = AGENT_WH;

-- Grant the user's role access to the agent
GRANT USAGE ON DATABASE oauth_passthrough_lab TO ROLE analyst_role;
GRANT USAGE ON SCHEMA oauth_passthrough_lab.main TO ROLE analyst_role;
GRANT SNOWFLAKE.CORTEX.ACTIVATE_AGENT
  ON AGENT oauth_passthrough_lab.main.my_agent
  TO ROLE analyst_role;

How Mapping Works

JWT ClaimSnowflake Attribute
upn: alice.smith@contoso.comlogin_name: alice.smith@contoso.com
roles: [analyst]User's DEFAULT_ROLE or granted roles

The mapping is case-insensitive. Snowflake looks up the user by login_name and establishes a session with that user's default role.

No Password Required

Users authenticated via External OAuth never need a Snowflake password. They can't log in via Snowsight or snowsql — their access is exclusively via token-based API calls.

This is ideal for external users who interact only through your application layer (Teams bot, web app, mobile app).

Calling the Agent with a Token

The API call that makes it all work — a standard Bearer token in the Authorization header.

# Obtain a token (MSAL device code flow for testing)
import msal

app = msal.PublicClientApplication(
    client_id="<your-app-client-id>",
    authority="https://login.microsoftonline.com/<your-tenant-id>"
)

flow = app.initiate_device_flow(
    scopes=["https://<account>.snowflakecomputing.com/.default"]
)
print(flow["message"])  # User visits URL and enters code

result = app.acquire_token_by_device_flow(flow)
access_token = result["access_token"]
# Call the Cortex Agent REST API with the Bearer token
import requests

response = requests.post(
    "https://<account>.snowflakecomputing.com/api/v2/cortex/agent:run",
    headers={
        "Authorization": f"Bearer {access_token}",
        "Content-Type": "application/json",
    },
    json={
        "agent_name": "oauth_passthrough_lab.main.my_agent",
        "messages": [{"role": "user", "content": "Show my sales data"}]
    }
)

Key insight: The agent session runs as alice.smith@contoso.com — not a service account. Any row access policies, masking policies, or role-based grants apply exactly as if Alice logged in directly. The agent can only access data Alice is authorized to see.

AgentCore Relay Pattern

How AWS AgentCore (or any orchestrator) forwards the user's token to Snowflake.

# AgentCore tool implementation that relays the user's token
class SnowflakeAgentTool:
    def invoke(self, query: str, user_context: dict) -> str:
        # The user's OAuth token is available in the context
        # AgentCore preserves it from the Teams/app authentication
        user_token = user_context["oauth_token"]

        response = requests.post(
            f"https://{SNOWFLAKE_ACCOUNT}.snowflakecomputing.com/api/v2/cortex/agent:run",
            headers={
                "Authorization": f"Bearer {user_token}",
                "Content-Type": "application/json",
            },
            json={
                "agent_name": "my_db.my_schema.my_agent",
                "messages": [{"role": "user", "content": query}]
            }
        )
        return response.json()

Why Relay?

  • AgentCore authenticates the user at the Teams layer
  • The same token is forwarded to Snowflake — no service account needed
  • Snowflake sees the real user identity on every request
  • Token refresh is handled by AgentCore/MSAL, not Snowflake

Architecture Benefit

  • Zero credential management in AgentCore
  • No Snowflake service account password to rotate
  • Each user's privileges enforced automatically
  • Full audit trail: Snowflake sees Alice, not service_bot

Error Cases & Troubleshooting

Common failure modes and how to diagnose them.

401 Invalid Audience

The aud claim in the JWT doesn't match EXTERNAL_OAUTH_AUDIENCE_LIST. Fix: ensure the app registration's Application ID URI matches the audience configured in Snowflake.

401 Token Expired

The JWT's exp claim is in the past. Fix: implement token refresh in your app layer (MSAL handles this automatically with acquire_token_silent).

401 User Not Found

The upn claim doesn't match any Snowflake user's login_name. Fix: create the user with the matching login_name, or check for case/domain mismatches.

403 Insufficient Privileges

Token is valid and user maps correctly, but the user's role lacks access to the agent or data. Fix: grant SNOWFLAKE.CORTEX.ACTIVATE_AGENT and necessary data privileges.

401 Signature Validation Failed

The JWS keys URL returns keys that don't match the token signature. Possible causes: wrong tenant ID in the integration, or a stale JWKS cache (Snowflake refreshes periodically).

400 Integration Disabled

The security integration has ENABLED = FALSE. Fix: ALTER SECURITY INTEGRATION entra_oauth_int SET ENABLED = TRUE.

Combining with Multi-Tenancy

Token passthrough + session attributes = authentication + authorization in one call.

# Pass both the user's OAuth token AND session attributes
response = requests.post(
    "https://<account>.snowflakecomputing.com/api/v2/cortex/agent:run",
    headers={
        "Authorization": f"Bearer {user_token}",
        "Content-Type": "application/json",
    },
    json={
        "agent_name": "my_db.my_schema.tenant_agent",
        "messages": [{"role": "user", "content": "Show revenue trends"}],
        "variables": {
            "tenant_id": {
                "value": "acme_corp",
                "is_immutable_session_attribute": true
            }
        }
    }
)

Authentication (Token)

  • Proves who the user is (cryptographic proof)
  • Maps to a Snowflake user with specific roles
  • Enables per-user audit trails
  • Enforces role-based grants (RBAC)

Authorization (Session Attributes)

  • Defines what data the user can see
  • Drives row access policies (tenant filtering)
  • Drives masking policies (column-level)
  • Immutable — can't be altered by the agent

Best of both worlds: The token gives you cryptographic identity proof and per-user audit trails. Session attributes give you fine-grained data filtering without creating per-user roles. Together they cover the full authentication + authorization stack.

Best Practices

Production patterns for secure, reliable token passthrough deployments.

Always Validate Audience

Set EXTERNAL_OAUTH_AUDIENCE_LIST to your specific Snowflake account URL. Never use a wildcard. This ensures tokens issued for other services can't be replayed against your Snowflake account.

Handle Token Refresh

Entra ID access tokens expire in ~60-90 minutes. Your app must use acquire_token_silent (MSAL) to refresh before expiry. Never cache tokens without checking expiration.

Map Users Proactively

Pre-create Snowflake users for all Entra ID users who need agent access. An unmapped user gets a hard 401 — there's no graceful fallback. Automate user provisioning via SCIM or a sync script.

Least-Privilege Roles

Each mapped user should have a role with minimal grants: access to the agent, the semantic view, and nothing else. Don't grant ACCOUNTADMIN to OAuth-authenticated users.

Monitor with Usage History

Query CORTEX_AGENT_USAGE_HISTORY to see which real users are calling the agent, token counts, and costs. This view shows the mapped user — giving you true per-person attribution.

Combine Patterns

Use token passthrough for authentication (who is this?) and session attributes for authorization (what can they see?). They're complementary, not competing approaches.
