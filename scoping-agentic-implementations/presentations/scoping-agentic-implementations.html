Part 1

Discovery: Understanding What to Build

The Scoping Funnel

Every successful agent project starts broad and narrows. Each layer increases specificity, measurability, and confidence.

1 Business Vision "We want our team to talk to their data"
2 Personas Who specifically? What's their data literacy?
3 Questions What will they actually ask? How complex?
4 Tools Which capabilities does each question type need?
5 Agent Spec Boundaries, success criteria, eval dataset

Anti-pattern: Jumping from "talk to your data" directly to tool selection. Without understanding personas and their questions, you build an agent that's impressive in a demo but doesn't solve the problems users actually have.

Persona Mapping

Different users ask fundamentally different questions. Map each persona before deciding what to build.

For Each Persona, Capture:

  • Role & responsibility — what decisions do they make?
  • Data literacy — can they interpret raw numbers or need narrative?
  • Current workflow — how do they get answers today?
  • Frequency — daily power user or occasional explorer?
  • Stakes — what happens if the answer is wrong?

Example Persona Card

  • Name: Regional Sales Manager
  • Literacy: Reads dashboards, doesn't write SQL
  • Current workflow: Asks analyst team, 2-day turnaround
  • Frequency: 5-10 questions/week
  • Stakes: Territory allocation, quota decisions
  • Success signal: "I got the answer without filing a ticket"

Key insight: The persona's success signal is your north star metric. A regional sales manager doesn't care about SQL correctness — they care that the territory numbers match what they'd get from their analyst. Frame evaluation around their definition of "right."

Question Taxonomy

Categorize the questions each persona will ask. This taxonomy directly determines tool selection, eval coverage, and phased delivery scope.

Category Example Complexity Data Source Wrong-Answer Cost
Lookup "What was Q2 revenue for the West region?" Low Structured Medium
Aggregation "Compare YoY growth by product line" Medium Structured High
Reasoning "Why did NPS drop last month?" High Structured + Unstructured High
Policy/Process "What's our return policy for enterprise?" Low Unstructured Very High
Out of Scope "Write me a marketing email" N/A N/A Reputational

Why This Matters for Scoping

  • Each category maps to a different Snowflake tool
  • Wrong-answer cost determines eval priority
  • Complexity tiers inform phased delivery
  • Out-of-scope definition prevents scope creep

How to Build Your Taxonomy

  • Interview 3-5 users per persona (15 min each)
  • Ask: "What did you ask your analyst last week?"
  • Review Slack/Teams channels for data questions
  • Check existing dashboard usage for implicit questions
  • Have PMs brainstorm high-value questions

Part 2

Specification: Defining What to Build

From Questions to Tools

Your question taxonomy directly maps to Snowflake primitives. Let the questions drive tool selection, not the reverse.

Question Category Primary Tool What It Does Prerequisite
Lookup / Aggregation Semantic View + Cortex Analyst Text-to-SQL over structured data with semantic context Well-described semantic view with verified queries
Policy/Process Cortex Search Hybrid search over unstructured documents Documents chunked and indexed in a search service
Reasoning Multi-tool Agent Orchestrates Analyst + Search + reasoning Both structured and unstructured sources ready
Out of Scope Agent Instructions Explicit refusal boundaries in system prompt Clear definition of what the agent should NOT do

Anti-pattern: Wiring up every tool "just in case." Each tool adds evaluation surface area, latency from unnecessary tool calls, and maintenance burden. If your taxonomy shows 80% of questions are structured lookups, start with Semantic Views + Cortex Analyst alone. Add tools when the taxonomy demands it.

Prerequisite audit: Before committing to a tool, check that its prerequisites are achievable. A Semantic View requires well-modeled tables with clear column descriptions. Cortex Search requires documents to exist in a parseable format. Missing prerequisites are the #1 cause of POC delays.

The Agent Spec Document

The spec is your contract between business stakeholders and the technical team. It answers: what are we building, for whom, how will we know it works?

Agent Name [e.g., sales_insights_agent]
Owner [Team and individual responsible for quality]
Personas Served [List of persona cards this agent targets]
Question Categories [Which taxonomy rows this agent handles]
Tools [Semantic Views, Search Services, Skills configured]
Out of Scope [Explicit boundaries: what the agent will refuse]
Business Success Metric [e.g., "80% of users get answers without filing a ticket"]
Technical Success Metrics [answer_correctness >= 0.80, tool_selection_accuracy >= 0.90]
Eval Dataset [Pointer to seed eval questions, target coverage per category]
Phase 1 Scope [Minimum viable slice: which personas + categories ship first]
Tenant Model [single-tenant / multi-tenant-internal / multi-tenant-external]
Access Control [Session attributes, Row Access Policies, Column Masking needed?]

Why this matters: Without a spec, scope creeps via "can it also..." requests. The spec gives you a clear "yes, that's Phase 2" response. It also gives evaluations a target — you can measure progress against the spec's defined success criteria rather than vague "is it good enough?" conversations.

Where Seed Questions Come From

  • PM intuition: "What would a VP ask on Monday morning?"
  • Analyst backlog: Most-asked questions from data team tickets
  • Dashboard implicit Qs: Every chart answers a question — write them down
  • Edge cases: Questions you know will be tricky (date ranges, nulls, ambiguity)
  • Refusals: Questions you know should be out of scope

Target Coverage (30-50 questions)

  • 60% happy-path questions across all categories
  • 20% edge cases and high-stakes scenarios
  • 10% multi-tool coordination questions
  • 10% out-of-scope refusal questions

Use AI_COMPLETE to draft ground-truth answers from your data, then have SMEs validate and correct. Don't let perfect be the enemy of shipped.

Speed over perfection: A 30-question eval dataset you ship this week is infinitely more useful than a 200-question dataset that takes a month to curate. Start with PM/tech intuition, ship, observe what breaks in practice, and add those failures back to the dataset. The flywheel is the product.

Part 3

Iteration: Measuring and Expanding

Measuring What Matters

Map business goals to technical metrics. Every success criterion in your spec should have a corresponding measurable signal.

Business Goal Technical Metric How to Measure
Users self-serve instead of filing tickets Conversation completion rate + answer_correctness Observability events + eval runs
Reduce time to insight Latency P50/P95 + tool_selection_accuracy Agent usage history + eval metrics
Trust the numbers Answer correctness on high-stakes category Per-category eval scoring
Don't generate compliance risk Refusal accuracy on out-of-scope Eval dataset with refusal questions
Predictable cost at scale Tokens/interaction + warehouse credits/query CORTEX_AGENT_USAGE_HISTORY + QUERY_ATTRIBUTION_HISTORY

The connection: Your scoping funnel (personas → questions → tools) determines what to build. Your agent spec defines success criteria. Your eval dataset + observability views measure whether you're meeting those criteria. The entire chain is traceable from "the VP wants to talk to their data" to "answer_correctness on aggregation questions is 0.87 this week."

Observability-Driven Iteration

Once deployed (even to a pilot group), observability data reveals the gap between your taxonomy assumptions and reality.

What You Assumed (Taxonomy)

  • 70% lookup, 20% aggregation, 10% reasoning
  • Primary persona: Sales Managers
  • Peak usage: Monday mornings
  • Out-of-scope: rare (<5%)

What You Observe (Reality)

  • 40% lookup, 30% aggregation, 20% reasoning, 10% ???
  • Surprise persona: Finance team discovered it
  • Peak usage: End of month (reporting)
  • 15% questions hit refusal or fail silently

The iteration flywheel:

1. Query CORTEX_AGENT_USAGE_HISTORY to see actual question distribution

2. Identify questions the agent handles poorly (low scores, high token usage, user abandonment)

3. Add representative failures to your eval dataset

4. Improve the agent (better instructions, new tools, refined semantic view)

5. Validate improvement via eval run before promoting

6. Deploy improved version, continue observing

-- Find questions where the agent used excessive tokens (potential confusion)
SELECT
    METADATA:'input'::STRING AS user_question,
    TOKENS_USED,
    METADATA:'interaction_interface'::STRING AS surface
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_AGENT_USAGE_HISTORY
WHERE AGENT_NAME = 'SALES_INSIGHTS_AGENT'
    AND TOKENS_USED > 5000  -- unusually high token usage
ORDER BY TOKENS_USED DESC
LIMIT 20;

Phased Delivery

Ship narrow, prove value, expand. Each phase has explicit entry criteria tied to eval scores from the previous phase.

Phase 1: Prove Value

Single persona, single tool (typically Semantic View + Analyst for structured data). Prove the agent answers the most common question category correctly.

Exit criteria: answer_correctness ≥ 0.75 on lookup questions, 5+ pilot users active weekly, seed eval passing in CI

Phase 2: Expand Coverage

Add tools (Cortex Search for documents, Skills for formatting). Cover the next tier of question complexity (aggregation, policy lookups).

Entry criteria: Phase 1 exit met. Exit: tool_selection_accuracy ≥ 0.85, answer_correctness ≥ 0.80 across all categories

Phase 3: Multi-Persona

Add routing/RBAC for new personas. May require agent routing (supervisor pattern) or row-level security on semantic views for data isolation.

Entry criteria: Phase 2 exit met + new persona taxonomy complete. Exit: per-persona eval scores meet thresholds

Phase 4: Production Hardening

Resource budgets, CI/CD quality gates, scheduled regression testing, SLAs, cost attribution tags, runaway query protection.

Entry criteria: Phase 3 exit met + observability baseline established. Exit: SLA met for 30 consecutive days

Why phases work: Each phase delivers user value independently. If Phase 1 proves the agent isn't the right approach for a use case, you've invested weeks, not months. If it succeeds, you have eval data and observability baselines that de-risk every subsequent phase.

Scoping for Multi-Tenancy

If your agent serves multiple user groups with different data access, access control must be scoped into the spec from the start.

Decision gate: Will this agent serve multiple tenants (teams, customers, business units) who should NOT see each other's data? If yes, the items below become Phase 1 prerequisites.

Session Attributes

Immutable identity passed at API call time. Your app authenticates users, then passes tenant_id / user_role as session attributes when calling the agent. Cannot be overridden by prompt injection.

Row Access Policies

Per-tenant data filtering enforced at the query engine level. The agent generates SQL freely — the RAP silently filters results to only the tenant's rows. No reliance on prompt instructions for security.

Column Masking

Sensitive columns (salary, SSN, commission rates) are masked or redacted based on tenant role. The agent never sees the raw values — masking is transparent and unforgeable.

Entitlements Table

Maps users/tenants to their allowed data access. User lifecycle is INSERT/DELETE on this table — no DDL, no per-user roles, no per-user grants. Scales to 10K+ tenants.

Cortex Search limitation: Row Access Policies do NOT apply to Cortex Search (vector index bypass). If your agent uses document retrieval with tenant-specific access, you need per-tenant search services or pre-filtered source tables. Plan for this in your tool selection.

Add to your spec: Tenant model (single/multi), identity mechanism (session attributes), which tables need RAPs, which columns need masking, and whether Cortex Search needs tenant isolation. These become Phase 1 prerequisites if multi-tenancy is required from launch.

Workshop Exercise

Apply the scoping funnel to your own use case. 60 minutes, five activities.

Activity 1: Persona Mapping (10 min)

Identify 2-3 personas. For each: role, data literacy, current workflow, frequency, stakes, success signal. Pick ONE persona for Phase 1.

Activity 2: Question Brainstorm (15 min)

Brainstorm 15-20 questions your Phase 1 persona would ask. Categorize each (lookup, aggregation, reasoning, policy, out-of-scope).

Activity 3: Synthetic Expansion (10 min)

Use AI_COMPLETE to generate new questions per category and variations of existing questions. Grow from 15 to 40+ eval questions.

Activity 4: Eval Dataset + Config (15 min)

Draft ground-truth descriptions, register dataset with SYSTEM$CREATE_EVALUATION_DATASET, configure eval metrics YAML.

Activity 5: Multi-Tenancy Assessment (10 min)

Answer: who shares this agent? How many tenants? Which tables/columns need access control? What session attributes identify the user?

Output: A first-draft agent spec with: target persona, question taxonomy, 40+ question eval dataset registered natively, multi-tenancy requirements, and Phase 1 scope. This is enough to start building and iterating immediately.
